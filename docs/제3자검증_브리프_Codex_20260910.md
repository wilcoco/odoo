### 배경 (판단에 필요한 사실)
- 이 코드는 **이미 운영 서버에 배포되어 있습니다.** 결함을 찾으면 "배포 후 발생 가능한 증상"을 함께 적으십시오.
- 자동차 부품 사출 공장의 IATF 16949 / 현대·기아 SQ 평가 대응 시스템입니다. **없는 실적을 데이터로 만들어내는 경로**(데모 데이터, 미래 날짜 기록, 미판정을 '양호'로 집계)는 허위기재로 취급되어 치명적입니다.
- 이 범위는 여러 브랜치를 통합 브랜치(`merge/20260909`)로 묶어 충돌을 해결한 결과입니다. **충돌 해결 과정에서 한쪽 기능이 조용히 사라졌는지**가 주요 관심사입니다.
- Odoo 는 모델에서 필드를 지워도 DB 컬럼을 남깁니다. `required=True` 였던 필드를 지운 경우 마이그레이션에서 `DROP COLUMN` 을 해야 하며, 안 하면 신규 insert 가 전부 실패합니다.
- 설계 규칙은 `addons_custom/CLAUDE.md` 에 있습니다. 먼저 읽으십시오.

### 검토 항목 (우선순위 순)

**1. 충돌 해결의 정합성** — `db9df608d6f` (34파일), `259871670e7` (21파일)
- 양쪽 브랜치의 기능이 모두 남아 있는가. 특히 `iatf_menu/views/menu.xml` 의 메뉴, `addons_custom/CLAUDE.md` 의 규칙, `account_kr_reports` 의 승인번호 로직(18.0.1.5.1)
- 같은 XML id 가 두 번 정의되거나, 한쪽 브랜치의 필드 참조가 다른 쪽 모델에 없는 경우

**2. 권한·sudo** — PR #35 (`a363aa13836`)
- `iatf_control_plan`, `iatf_ppap`, `iatf_process_inspection`, `iatf_training` 의 `mrp_production.py` 에 추가된 `sudo()` 4곳이 **회사(company) 로 한정**되어 있는가. 다른 회사 데이터를 읽거나 만들 수 있는 경로가 있는가
- `injection_planning/security/security.xml` 의 새 권한 그룹 3단계(사용자/관리자/디버그 관리자)가 `ir.model.access.csv` 와 일치하는가. 디버그 관리자가 아닌 사용자가 데이터 수정·삭제할 수 있는 우회 경로가 있는가

**3. 마이그레이션**
- `iatf_equipment/migrations/18.0.1.1.0`, `18.0.1.3.0`, `iatf_work_environment/migrations/18.0.1.3.0`
- 멱등한가(두 번 실행해도 안전한가). 사람이 입력한 값을 덮어쓰지 않는가
- Odoo 가 새 컬럼에 기본값을 먼저 채우는 점을 고려했는가 (`COALESCE(col, ...)` 는 이 경우 NULL 을 못 잡는다)

**4. 허위기재 경로**
- `iatf.check.record`, `iatf.mold.check`, `iatf.blend.log` 에서 미래 날짜 기록, 판정 없는 라인의 '완료' 처리, 상·하한 밖 측정값에 '양호' 저장 — 이 세 가지가 **서버 측 constrains** 로 막혀 있는가 (뷰의 readonly 만으로는 부족)
- `iatf.check.sheet.item` 의 기준(상·하한·주기)을 편집했을 때 **이미 완료된 실적의 판정이 바뀌는가** (바뀌면 안 된다)
- `iatf.check.sheet.revision` 을 관리자 권한 사용자가 수정·삭제할 수 있는가 (없어야 한다)

**5. 롤백 수정** — `fix/tax-invoice-row-rollback`
- `account_kr_reports/wizard/tax_invoice_import.py` 의 세이브포인트가 행 단위 격리를 실제로 보장하는가. `mv.flush_recordset()` 위치가 맞는가 (세이브포인트 안이어야 지연 제약이 안에서 터진다)
- 게시(`action_post`) 건별 격리에서 부분 성공 시 결과 집계가 정확한가

**6. 테스트 커버리지**
- 각 모듈 `tests/` 가 위 4·5번 경로를 실제로 검사하는가, 아니면 해피패스만 보는가
- `assertRaises` 가 너무 넓은 예외(`Exception`)를 잡아 잘못된 이유로 통과하는 테스트가 있는가
