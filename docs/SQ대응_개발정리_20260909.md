작성 2026-09-09 · 대상 기간 2026-09-01 ~ 09-09 · 저장소 `wilcoco/odoo` 18.0

## 0. 전제 — 이 전제가 우선순위를 뒤집었다

| 전제 | 결과 |
|---|---|
| 준비 기간 약 1개월 | 배점 큰 것부터 |
| **아직 공장 가동 전** — 이행실적을 쌓을 수 없다 | **"실적을 쌓는 기능"보다 "기준을 담는 마스터"를 먼저** |
| 데모·샘플 데이터로 실적을 채우면 안 됨 | 채점표에 "허위기재 시 다수미흡(25%)" 명시 |
| 신규 모듈 금지 | 금형은 `iatf_mold` 확장, 점검은 공통 모델 하나 |

SQ 채점은 **우수 100% / 양호 80% / 보완 60%** 이고, 우수와 양호를 가르는 조건이
**"이행실적의 정기적 이상유무 확인 또는 지속 모니터링"** 이다.
종이·수기로는 80%가 천장이고, 시스템 기록·집계·이상탐지가 있어야 100%다.

> **가동 전이므로 지금 확보한 것은 우수(100%)가 아니라 "보완(60%) 추락 방지"다.**
> 그릇을 만들고 기준을 담아 "기준 없음"으로 깎이는 것을 막았다. 100%는 가동 후 실적이 쌓여야 나온다.

## 2. 기능별 기획 의도와 명세

### 2-1. 금형 관리 (SQ 4_1·4_2·4_5·4_6·4_7 — 130점 영역)

**모델**: `iatf.mold`(확장) · `iatf.mold.check` · `iatf.mold.check.line` ·
`iatf.mold.temp.log` · `iatf.mold.tryout` · `iatf.mold.maintenance`(확장)

**기획 의도** — 대장은 있는데 이력이 없어 "기준은 있고 실적 없음" 판정을 받으면 보완(60%) 이하로
떨어진다. 그래서 **대장에 점검·세척·예열·온도 이력을 붙이는 확장**으로 갔다. 신규 모듈이 아니다.

`iatf.mold` 에 추가된 관리기준:
```
grade                A/B/C 관리등급
check_cycle_days     일상점검 주기(일)
clean_cycle_days     세척 주기(일)
preheat_temp_min/max 예열 상·하한(℃)
mold_temp_min/max    금형온도 상·하한(℃)
```
계산 필드로 `last_check_date` · `next_check_due` · `is_check_overdue`,
`last_clean_date` · `next_clean_due` · `is_clean_overdue`, `last_tryout_date`.

**핵심은 "누락 집계"다.** 동종업체 감점 사유가 "점검표 작성 일부 누락"이었다.
기한 경과 금형 목록이 화면에 나오는 것이 곧 "지속 모니터링" 증빙이 된다.

세척은 별도 모델을 만들지 않고 `iatf.mold.maintenance.maintenance_type` 에 `clean` 을 넣었다.
`clean_cycle_days` 와 짝이 되어 SQ 4_2(계획 대비 실적)를 이룬다.

온도 이력(`iatf.mold.temp.log`)은 **측정 부위(고정측/이동측)와 방식(적외선/접촉식/설비센서)을
필수 기록**하게 했다. 동종업체 지적이 "적외선 온도계 고정측/이동측 측정 방식 개선 필요"였기 때문에,
그 지적을 선제 차단하는 구조다.

> **미해결 — 주기 기준 불일치.** 회사 IATF 관리항목표의 금형 일상점검 주기는 **"금형교환시"**(이벤트)인데
> 구현은 **일 단위**다. 대표 판단으로 일단 날짜 주기를 유지하기로 했으나, 누락 집계의 기준 자체가
> 어긋나 있다. 새 공장 운영 방식이 정해지면 이벤트 기준을 선택지로 넣어야 한다.

### 2-2. 범용 점검 일지 (SQ 3_3·3_4·1_7·6_8·6_9 + 조립장 1_5·1_6·5_1)

**모델**: `iatf.check.sheet` · `iatf.check.sheet.item` · `iatf.check.record` · `iatf.check.record.line`

**기획 의도** — 전동공구 토크, 통전검사 마스터, 원소재 건조기 필터, 분쇄기·배합기, 냉각수·작동유,
조도, 3정5행, 소화기 — **대상만 다르고 구조가 같은 점검들을 모델 하나로 덮는다.**
대상별 전용 모듈을 만들면 항목이 늘 때마다 개발이 필요하다.

경계: 금형(`iatf.mold.check`)·설비 일상점검(`iatf.daily.check`)·5S(`iatf.environment.check`)는
각자 고유 구조가 있어 흡수하지 않았다.

설계상 지킨 것:
- **점검하지 않은 것과 이상 없는 것은 다른 사실이다.** 판정이 비면 '양호'가 아니라 '미완료'
- **완료(done) 건만 실적으로 센다.** 작성 중인 점검표는 실적이 아니다
- **미래 날짜 기록 차단.** 미래로 적으면 미실시 목록에서 사라진다 = 허위 선행기재 경로
- **한 번도 점검하지 않은 시트도** 운용 시작일 + 주기가 지나면 미실시로 잡힌다

### 2-3. 안전관리 (SQ 6_1 — 30점, 동종업체 최대 감점)

**모델**: `iatf.safety.assessment` · `iatf.safety.assessment.line` · `iatf.safety.incident`

위험성평가(유해위험요인 → 빈도×강도 → 감소대책) + 아차사고/사고 이력.
신규 모듈을 만들지 않고 `iatf_work_environment` 확장으로 붙였다.
안전점검(소화기·비상구·방호장치)은 주기·미실시 구조가 일반 점검과 같아
**네 번째 점검 원장을 만들지 않고** `iatf.check.sheet.is_safety` 플래그로 구분만 했다.

### 2-4. 분쇄·배합일지 (SQ 1_10·3_4)

**모델**: `iatf.blend.standard` · `iatf.regrind.log` · `iatf.blend.log` · `iatf.blend.log.line`

배합 관리기준(재생재 상한 등) + 분쇄일지 + 배합일지(투입 LOT 내역).
재생재 혼합은 고객 승인이 필요한 경우가 많아 그 연결을 뒀다(SQ 1_5).

### 2-5. 예비부품 분류체계 (머지 완료, 배포 대기)

**모델**: `iatf.spare.category` · `iatf.spare.application`

레거시 3대 문제를 각각 푼 것:

| 레거시 문제 | 해법 |
|---|---|
| 4계층(부문:공정:설비군:기종)을 SPMSRT **한 컬럼 4자리**에 담음 | 자리별 컬럼으로 쪼개고 `full_code` 를 재귀 계산으로 재현 (레거시 `AIAA` 표기 유지, 상위 자리 변경이 손자까지 전파) |
| 잎(부품 달리는 기종)과 가지(`A000`·`AA00`)를 같은 표에 섞음 | `is_leaf` + **양쪽 모델 모두에** constrains |
| 분류 트리가 1:N 강제 | `iatf.spare.application` 다대다 적용표 신설, `spare.equipment_id`(required 1:N) 제거 |

> 분류는 "이 부품이 **어디에 속하는가**" 한 자리를 정하는 것이고,
> 적용표는 "이 부품이 **어디어디에 들어가는가**"를 여러 개 적는 것이다. 대체 관계가 아니라 둘 다 필요하다.

분류 트리를 `iatf.equipment` 와 합치지 않은 이유: 설비 대장은 **실물 인스턴스**이고 분류는
**카탈로그 타입**이다. 합치면 "UBE-2200T" 라는 유령 설비가 생긴다. `iatf.equipment.category_id`
로 두 체계를 잇는다.

### 2-6. 점검 양식 프레임 (전 점검 공통)

**모델**: `iatf.check.sheet.item`(확장) · `iatf.check.sheet.revision`(신규)

**기획 의도** — 회사 실제 양식(`'24년도 설비 일상점검표`, 시트 22장)을 보니 항목 구성이
공정·설비마다 전부 다르다. **양식을 코드에 박으면 설비가 하나 늘 때마다 개발이 필요하다.**

항목 정의에 추가한 것:

| 필드 | 회사 양식 근거 |
|---|---|
| 입력 방식(양호·불량 / 수치 기입 / 내용 기입) | 점검표의 '방법' 열(육안·수치기입·시연) |
| 기준 방식(정성 / 범위 / 하한 이상 / 상한 이하 / **목표±공차**) | 사출 작동유 `40℃±10℃`, 조립 AIR `0.4~0.6Mpa` |
| 항목별 주기 | 도장 믹싱룸 시트의 항목별 주기 열 |
| 중요 관리 항목 | 모든 시트 하단 `※ 금월 중요 관리 항목` |

기준 방식은 **표기**일 뿐이고 판정은 상·하한 한 갈래로만 돈다(목표±공차는 상·하한으로 환산 저장).
판정 로직을 갈라지지 않게 하기 위해서다.

**개정해도 과거 판정이 흔들리지 않게 한 것이 이 작업의 핵심이다.**
기준을 화면에서 고칠 수 있게 만드는 순간, `40±10` 에서 합격이던 47℃ 가 `40±5` 로 좁힌 뒤
불합격으로 보인다. 심사에서 "이 값이 왜 합격이었나"에 답할 수 없다.

막은 방법:
1. 실적 라인이 **판정 당시 기준을 복사**해 보유
2. 실적에 **몇 차 개정본으로 점검했는지** 기록
3. 개정 이력은 **관리자도 수정·삭제 불가**(ACL read-only, 생성은 sudo 경로만)

부수 효과로 개정 이력 자체가 SQ 1_1(표준류 일치성)·IATF 문서관리 증빙이 된다.

## 3. 설계 원칙 — 반복해서 적용한 것

### 3-1. 없는 실적을 만들지 않는다
데모·샘플로 실적을 채우면 허위기재(다수미흡 25%)다. 기준·계획·시스템으로 설명하는 편이 안전하다.
반대로 **기준값(상하한·주기)을 넣는 것은 허위기재가 아니다** — 회사가 실제로 쓰던 값이고
SQ 가 요구하는 '관리기준 수립' 증빙 그 자체다.

### 3-2. 0 은 '0개'가 아니라 '모름'이다
예비부품 수량이 집계되지 않은 상태를 0으로 표시하면 "재고 없음"으로 읽힌다.
`미집계` 로 구분해 표시한다.

### 3-3. 조용히 망가지는 경로를 막는다
| 경로 | 왜 나쁜가 |
|---|---|
| 상·하한만 주고 기준 방식을 안 줌 | 기본값 '정성'이 되어 기준이 화면엔 보이는데 판정에 안 쓰인다. **기준이 없는 것보다 나쁘다** |
| 방식과 어긋난 경계값 | 조용히 0으로 지우면 원인을 못 찾는다. 지우지 않고 이유를 말하고 막는다 |
| 수치 기준 + 양호·불량 입력 | 측정값 칸이 없어 눈대중 판정이 된다 |
| 폼 domain 만으로 제한 | 엑셀 가져오기·API 는 통과한다. 서버 constrains 로 백스톱 |

### 3-4. 우회 경로를 양쪽에서 막는다
부품에 `@api.constrains("category_id")` 만 걸면, 부품은 그대로 두고 **분류의 `level` 을 바꿔**
묶음 노드로 만드는 우회가 열린다. 양쪽 모델 모두에서 막는다.

## 4. 검증 방식 — 신규 설치로는 안 잡히는 것들

### 4-1. 기존 DB 복제 → 실데이터 심기 → 업그레이드
새 DB 에 설치해서 잘 도는 것은 증거가 약하다. 운영은 **데이터가 든 DB 를 업그레이드**하는 것이다.
`cams_stg` · `blend1` 등을 복제해 레거시 행을 SQL 로 심고 업그레이드했다.

**이 방식으로만 잡힌 결함 2건:**

1. **지운 필드의 컬럼 잔재** — `spare.equipment_id`(required)를 제거했는데 Odoo 는 컬럼을 남긴다.
   NOT NULL 이 남아 **예비부품을 새로 등록할 때마다 insert 가 실패**한다.
   로컬 새 DB 에서는 안 보이고 운영 업그레이드에서만 터진다.
2. **마이그레이션이 헛돎** — Odoo 는 새 컬럼에 **필드 기본값으로 기존 행을 먼저 채운다.**
   그래서 `COALESCE(NULL 검사)` 로는 "기본값이 박힌 상태"를 못 잡는다. 실적 라인이 이관되지 않았다.

### 4-2. 적대적 검증
해피패스만 보면 놓친다. **반드시 `env.cr.savepoint()` 안에서** 돌려야 한다 —
제약이 걸려도 그 전에 나간 UPDATE 는 DB 에 남아 다음 검사를 오염시킨다.
(분류체계 적대적 검증 1차에서 이 함정 때문에 가짜 FAIL 15건이 났다. 코드 결함이 아니었다.)

### 4-3. 테스트 3종 + 단계별 인계
각 기능마다 ①정상 기록 생성 ②기한 경과 판정 ③상·하한 벗어난 값의 합부 판정.
단계가 끝나면 `docs/신호_테스트세션_할일.md` 에 회신하고 **테스트 세션 검토를 거친 뒤** 다음 단계로 간다.
(양식 프레임 → `review/check-sheet-frame`, 5개 시나리오 전부 통과)

### 5-2. 다음 개발 단계 (검토 통과, 착수 가능)
1. 회사 `'24년도 설비 일상점검표` **22개 시트 적재** — 사출·도장·조립 전부 (대표 결정)
2. 금형 일상점검을 **양식 프레임으로 이관** (대표 승인)
3. **IATF 관리항목(138개) × SQ 평가항목 두 축 매핑**

3번의 기획 의도: IATF 는 시스템 인증(프로세스 × 관리항목 축), SQ 는 고객 평가(6영역 × 배점 축)다.
**겹치는 건 원천 기록이고 다른 건 그걸 묶는 축이다.** 지금 코드는 SQ 항목번호가 모델 설명에
박혀 있어 축이 하나뿐이다. 기록 위에 라벨 두 개를 다는 얇은 층을 `iatf_audit` 에 붙인다.

### 5-3. 아직 비어 있는 것 (배점 합 대략 100~120점)
| 항목 | 배점 |
|---|---|
| 1_8 초기 허용불량 기준·이력 | 20 |
| 6_7 개선활동 등록·집계 | 20 |
| 6_12 정성품질 | 20 |
| 2_3 한도견본 | 10~20 |
| 6_10 리워크 관리대장 | 10 |
| 1_4 취약시간대 유효성 검증 / 2_4 정기신뢰성 계획 대 실적 | — |

> **개발보다 시트 채우기가 먼저다.** 범용 점검일지(3_3·1_7·6_8·6_9)는 아직 빈 그릇이고,
> 시트에 넣을 항목·주기·상하한은 현장 기준이라 지어내면 안 된다. 회사 양식에 이미 있다.
> 개발 없이 담당자 입력만으로 4개 항목이 살아나므로 배점당 효율이 가장 높다.
