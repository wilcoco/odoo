# 회사운영 전영역 시뮬레이션 — 테스트 계획서

작성: 2026-07-02. 대상 시스템: CAMS Odoo 18 ERP/MES (사출·조립·품질·SCM·정산).
목적: **회사가 실제로 돌아가는 방식 그대로** 전 영역(기준정보→수요→생산→품질→IATF/SQ→입고→정산→마감)을 시뮬레이션하여 시스템이 업무를 빠짐없이 지원하는지 검증하고, 갭을 문서화한다.

관련 문서: `ERP_비즈니스로직_정리.md`(모듈별 로직), `회사운영_종합시뮬레이션_보고서.md`(1차 시뮬, 2026-06), 본 계획의 결과보고서(시뮬 후 작성).

## 1. 회사가 돌아가는 방식 (업무 모델 정리)

### 1.1 회사 개요
현대차 협력 자동차부품 사출·도장 공장. 원청(현대)로부터 생산요청(BR)/수요계획(Oracle T_ZM_PLN1 시간별·PLN2 일별)을 받아 **사출 → 조립 → 출하**한다. 원재료(수지)는 사일로로 입고되고, 외주부품(체결구·클립 등)은 협력사로부터 공급받는다.

### 1.2 핵심 업무 원칙 (⚠️ 표준 Odoo와 다른 회사 특수 모델)
1. **발주-입고-재고-마감 구조가 아니다.** 정식 구속력 있는 발주(PO)로 돌지 않는다.
2. **협력사 부품 마감 = 생산량 기준.** 원청 BR/수요 → 완제품 생산량 → **BOM 전개** → 소요자재 산출 → 그 수량으로 협력사 정산(매입계산서). 입고는 받되 입고량이 아니라 **생산에 쓰인 양**이 정산 기준.
3. **원재료(수지)는 예외 = 톤당 마감.** 사일로로 입고되는 원재료는 부품정산에서 제외하고 **납품 톤 × 계약 톤단가**로 별도 월정산.
4. **자동 재주문 = 소요예상 통보(구속력 없음).** 사일로 저재고 시 협력사에 소요예상을 통보하는 **보조자료**일 뿐, 납품 책임은 원청 계획을 아는 공급사에 있다.
5. **생산은 2단계 MO.** 계획 MO(배치·스케줄링 단위) 아래 PLC가 단위 MO(개당 1개, 14자리 시리얼)를 대량 생성. 협력사 부품정산은 **조립 MO에서만** 발생(사출 MO는 수지만 소비 → 톤정산 영역).

## 4. 시나리오 (단계별 절차·검증항목·판정기준)

### S1. 수요 접수 → 생산계획 (①②)
1. 원청 수요 등록: FIN-A 120개/일 × 5일, FIN-B 80개/일 × 5일 (production.demand, draft)
2. BOM 전개 실행 → 사출부품·외주부품 소요 산출 확인
   - **기대**: INJ-SHELL-A 600, INJ-BRKT-B 800, OUT-FST-C 3,200(=600×4+400×2), OUT-CLP-D 3,600
3. 사출 스케줄링 실행 → 금형/사출기 배정, 일산 capa 대비 배분 확인
- **판정**: 전개수량 정확 / 스케줄 라인 생성·배정 합리성

### S2. 사출 생산 (③④ 전반)
1. 계획 MO 생성(INJ-SHELL-A 600 등) → 확정
2. 단위 MO 흐름 대표 검증(일부만): is_ip_unit_mo=True MO 생성·완료 — 채터 비활성/시리얼 확인
3. 계획 MO 완료 → 수지 소비 확인: 600×3.2+800×1.1 = **2,800kg** → SILO 12,000→9,200(주의) 확인
4. **검증**: 사출 MO에서 vendor.mrp.accrual **0건**(원재료 제외+단위MO skip) — 회귀 확인
- **판정**: 소비량 정확 / 사일로 잔량·수준 정확 / 사출 MO 정산 0

### S3. 소요예상 통보 → 협력사 납품 → 입고·충전 (④⑤)
1. 사일로 추가 소비로 재주문점(6,000) 이하 유도 → cron 실행 → **소요예상 통보 자동생성** 확인(구속력 없음 문구, 중복통보 방지)
2. 협력사(한수지) 납품 → PO(silo_id 지정)+입고 처리 → **자동충전**·적재로그(load.log) 생성 확인
3. 외주부품 납품: 대한체결·미래클립 입고 (부품은 일반 재고)
4. **납품 실패 시나리오**: 미래클립 PO 1건 납기경과 미입고 → 지연감지 cron → delivery_overdue 알림 + 영향 MO 식별 확인
5. 협력사 포탈: 토큰 접속 → 발주확인→출하 응답 상태흐름 확인(가능 범위)
- **판정**: 통보 자동생성·중복방지 / 충전·로그 정확 / 지연감지 정확

### S4. 조립 생산 (⑥)
1. 조립 MO(FIN-A 600, FIN-B 400) 생성·완료 → 부품 재고 차감 확인(사출부품+외주부품)
2. 완제품 재고 입고 확인
3. **조립 MO 완료 시 vendor.mrp.accrual 생성** 확인: OUT-FST-C 3,200×계약단가, OUT-CLP-D 3,600×계약단가 — **원재료(수지)는 accrual에 없음**
- **판정**: 재고 흐름 정확 / accrual 수량·단가(계약단가) 정확 / 이중생성 없음(재완료·복사 가드)

### S5. 품질 이슈 → IATF 반영 (⑦)
※ 코드 분석 결과(비즈니스로직 문서 PART3-H): 검사(IPQC/FQC) fail→NC는 **자동**(production_id 자동), quality.alert→NC는 **수동 승격**(production_id 미복사). 두 경로 모두 검증한다.
1. **주경로(자동)**: 사출 MO 완료 → FQC(iatf.process.inspection) 자동생성 확인 → fail 판정 → **NC 자동생성 + production_id 연계** 확인 + 로트 자동격리 확인
2. **보조경로(수동)**: quality.alert 생성 → action_promote_to_nonconformity 승격 → 양방향 링크 확인 (production_id 미복사 = 알려진 갭 재확인)
3. 시정조치(corrective action) 생성·상태흐름(8D 게이트: D3/D4 필수, CA verified 전 종결차단) 확인
4. IATF 대시보드/집계에 NC 반영 확인
- **판정**: 검사 자동생성 / fail→NC 자동+MO 추적 / 8D 게이트 / 브리지 수동 동작

### S6. 수입검사 불합격 → SQ 반영 (⑧⑨)
1. 대한체결 입고분 수입검사(iatf_incoming_inspection) — 1건 합격, 1건 **불합격** 처리
2. 불합격 → 협력사 부적합/클레임 흐름 확인 (iatf_supplier_quality / iatf_outsource)
3. **sq_evaluation**: 품질·납기 실적으로 협력사 평가 실행 — 불합격·납품지연이 점수/등급에 반영되는지 확인
- **판정**: 검사 합불 처리 / SQ 데이터 연계(자동인지 수동인지 명시) / 평가 산출

### S7. 월 마감 — 부품 정산 (⑩)
1. 정산 위저드 실행(기간=당월) → 협력사별 accrual 집계 → **매입계산서(in_invoice) 생성**
   - **기대**: 대한체결 3,200×단가, 미래클립 3,600×단가
2. 멱등성: 위저드 재실행 시 이중 청구 없는지
3. 계산서 게시 → 채무 반영
- **판정**: 금액 정확(계약단가) / 중복 없음 / 회계 전기

### S8. 월 마감 — 원재료 톤당 정산 (⑪)
1. raw.material.settlement 생성(당월) → 집계 → **적재로그 기준** 납품 톤 확인 (월경계: 전월 적재분 미포함 검증)
2. 확정 → 매입계산서 생성 (한수지: N톤 × 1,200,000)
3. 멱등성: 재집계 잠금·계산서 중복 차단 확인
- **판정**: 톤수 정확(로그 기준) / 금액 정확 / 가드 동작

### S9. 회계·대시보드 (⑫⑬)
1. 매입계산서 게시 → 나갈 돈(채무) 확인
2. cams_ops_dashboard: 재고(사일로/부품/완제품)·계획·MO진행·SCM(지연/통보)·품질(NC)·돈흐름(나간/나갈) KPI 값이 시뮬 실적과 일치하는지 대조
- **판정**: KPI ↔ 실제 데이터 일치

## 5. 판정 기준·산출물
- 각 단계 **Pass / Gap / N/A** + 근거 수치 기록.
- Gap = ①결함(고쳐야 함) ②미구현(추가개발 목록) ③수동절차(운영 프로세스로 흡수) 로 분류.
- 산출물: 결과 보고서(단계별 수치·판정·갭 목록), 발견 결함은 수정 브랜치/PR로 연결.

## 6. 리스크·전제
- IATF 모듈은 별도 세션에서 개발 진행 중(feat/iatf-company-forms) → 시뮬은 **현재 마운트본** 기준. 갭은 해당 세션에 인계.
- PLC/MQTT 실장비 없음 → 단위 MO는 대표 케이스만 코드로 생성(현장 대량생성은 범위 외).
- Oracle 수요연동은 별도 검증 완료(2026-06) → 이번엔 수요를 수동 등록으로 대체.
- 협력사 포탈 HTTP 흐름은 컨테이너 내부 호출로 확인(외부 노출 없음).
