## 3. 실제 실행 코드 (§4-A) — 미러가 **전면 미러**입니다

요청서가 "같은 기술명 모듈이 여러 경로" 를 지적한 것은 정확합니다. 규모를 실측했습니다.

- `odoo_gh/iatf_plugins/` 는 **wilcoco `addons_custom` 55개 전부를 포함**합니다(2개 모듈만 미러라는 과거 기록은 낡았습니다).
- 그 위에 **미러에만 있는 7개**: `account_kr_plus_patch` `cams_ops_dashboard` `cams_ops_process` `escon_eapproval` `escon_hr_common` `escon_mainmenu_do_redirect` `mrp_plus_patch`
  → 이들은 **정본에 없으므로 wilcoco 만 봐서는 존재 자체를 알 수 없습니다.**

**현재 드리프트(2026-09-10 실측): 55개 중 3개**

| 모듈 | 정본(wilcoco 18.0) | 미러(odoo_gh main) | 성격 |
|---|---|---|---|
| `pumui_approval` | 1.0.0 | **2.4.0** | 미러가 크게 앞섬 (모델·뷰 다수) |
| `escon_mainmenu` | 1.0.0 | **1.1.0** | 미러에 migrations 추가 |
| `supplier_portal_purchase` | 1.3.0 | 1.3.1 | 메뉴 XML 차이 |

→ **결론: 정본 커밋만으로 배포 상태를 판정할 수 없다는 요청서의 전제가 맞습니다.**
같은 모듈이 두 경로에 있고 버전이 다르며, 어느 쪽이 로드되는지는 **운영 addons_path 순서**로 결정됩니다.

**요청**: 서버 담당이 운영의 `addons_path` 실제 값과, 해당 경로에서 읽히는
`iatf_plugins` / `odoo_plugins` / `addons_custom` 의 커밋 SHA(또는 파일 해시)를 회신해 주십시오.
이것 없이는 §4-A(실행 코드 확정)를 완료할 수 없습니다.

## 5. 통합시험 환경 설계에 반드시 반영할 제약 (요청서 미반영)

1. **UAT 를 운영 DB(odoo18)에서 진행 중**입니다. 라이선스상 DB 가 1개라 별도 UAT DB 를
   두지 못했고, 테스트로 만든 발주·전표가 **실번호를 소비**합니다.
   → §5-3 "검증 DB" 를 운영과 분리하려면 **덤프 복원본**을 쓰는 방식이어야 합니다.
2. **양산 개시 전**이라 이행실적 데이터가 없습니다. SQ 대응 개발도 "기준 마스터 +
   가동 전 실제 이력(금형 이관·시사출, 계측기 교정, 교육, 문서 개정)" 중심으로 진행 중입니다.
   → 통합시험의 기대값을 **과거 실적 기반으로 잡을 수 없습니다.**
3. **데모 데이터로 실적을 채우지 말 것** — SQ 채점에 "허위기재 확인 시 다수미흡(25%)" 이
   명시돼 있습니다. 시험 데이터는 반드시 시험임이 식별되어야 합니다.

## 6. §6 최소 합격 기준에 추가 제안 2건

이번 프로젝트에서 **실제로 발생한 사고 유형**이라 기준에 넣을 값이 있습니다.

1. **"테스트가 실행됐는지"를 확인한다** — 환경 조건(예: 계정과목표 미로드) 때문에
   테스트가 **조용히 skip 되면서 통과로 보이는** 사례가 있었습니다.
   합격 판정 시 skip 수를 함께 보고할 것.
2. **핵심 회귀 테스트는 사보타주 검증을 거친다** — 고친 코드를 되돌렸을 때 그 테스트가
   **실제로 실패하는지** 확인. (실사례: 세이브포인트 제거 시 실패함을 확인한 뒤에야
   행 단위 롤백 수정을 완료 처리)
3. (기존 기준 보강) **기존 DB 업그레이드 검증** — 신선 설치로는 안 잡히는 결함이 있습니다.
   Odoo 는 새 컬럼을 기본값으로 먼저 채우므로 `COALESCE(NULL)` 검사로는
   "기본값이 박힌 상태" 를 못 걸러 실적 라인 이관이 통째로 누락된 사례가 있었습니다.
