| | |
|---|---|
| 대상 | `escon-odoo/odoo_gh` → `iatf_plugins/account_kr_plus_patch` |
| 파일 | `models/sequence_repair_wizard.py` |
| 관련 PR | wilcoco/odoo #27 (이 모듈을 wilcoco 쪽으로 가져오는 PR). **#27 의 결함이 아니라 정본에 원래 있던 코드** |

---

## 1. 이 위저드가 하는 일

`account.kr.move.sequence.repair.wizard` — **이미 발급된 전표번호를 소급해서 다시 매기는** 도구입니다.

전표번호가 한국식 형식(`YYYY-MM-DD-순번`)에 맞지 않거나, 서로 다른 전표가 같은 날짜·순번을 중복 사용하고 있을 때, 회계 관리자가 조회 → 미리보기 → 적용 순으로 번호를 정리합니다.

기본 조회 대상이 **전기 완료(`state = 'posted'`) 전표**입니다.

```python
# sequence_repair_wizard.py:149  (_get_move_domain)
else:
    domain.append(("state", "=", "posted"))
```

적용 단계에서는 대상 전표의 번호를 **일괄로 비운 뒤** 새 번호를 하나씩 채웁니다. (같은 저널 내 번호 유일성 제약 때문에 필요한 순서입니다.)

```python
# sequence_repair_wizard.py:437-443
moves = lines.move_id.with_context(**repair_context)
moves.write({"name": False})
moves.flush_recordset(["name"])
for line in lines:
    line.move_id.with_context(**repair_context).write({
        "name": line.proposed_name,
    })
```

## 2. 문제 — 바꾼 흔적이 남지 않는다

위 코드의 `repair_context` 입니다.

```python
# sequence_repair_wizard.py:427-434
repair_context = {
    "kr_sequence_repair_only_name": True,
    "skip_is_manually_modified": True,
    "tracking_disable": True,      # ← 이 두 줄
    "mail_notrack": True,          # ←
}
```

`tracking_disable` / `mail_notrack` 때문에 **번호가 바뀐 전표의 chatter 에 아무 기록도 남지 않습니다.**

그리고 결과를 담는 `account.kr.move.sequence.repair.line` 은 `models.TransientModel` 입니다. 화면을 닫으면 사라지고, vacuum 이 돌면 DB 에서도 지워집니다.

**결과: 전기 완료된 전표의 번호가 바뀌었는데, 누가·언제·어떤 번호를 무엇으로 바꿨는지 시스템 어디에도 남지 않습니다.**

전표번호는 장부와 외부 증빙(세금계산서, 부가세 신고, 거래처 통보)을 잇는 식별자입니다. "바꿨다"는 사실 자체가 남아야 할 종류의 기록입니다.

---

## 3. 왜 지금 문제가 되나 — 가드가 기본값으로는 안 걸린다

위저드에는 보호 장치가 있습니다. `_get_block_reason()` 이 아래를 차단합니다.

| 가드 | 기본 상태 |
|---|---|
| `move.inalterable_hash` (해시 보호 전표) | **꺼짐** — `account.journal.restrict_mode_hash_table` 기본값 `False` |
| `_check_fiscal_lock_dates()` (회계기간 잠금) | **미설정** — 담당자가 잠금일을 지정해야 작동 |
| `line_ids._check_tax_lock_date()` (세금 잠금) | **미설정** — 위와 동일 |
| 저널 `sequence_override_regex` 충돌 | 해당 저널만 |
| 같은 저널 내 번호 충돌 | 항상 작동 |

**즉 해시도 잠금일도 설정하지 않은 흔한 구성에서는, 이미 부가세 신고에 들어갔거나 거래처에 세금계산서로 나간 전표번호도 변경 대상에 들어옵니다.** 그것이 잘못이라는 뜻은 아닙니다 — 정리가 필요해서 만든 도구니까요. 다만 **그 정도의 변경이라면 기록이 남아야 합니다.**

## 4. 등급을 낮춘 이유 (최초 🔴 → 🟠)

처음에는 `:149`(posted 대상)와 `:438`(name 을 False 로) 두 줄만 보고 🔴 로 판단했습니다. **코드 전체를 다시 읽고 하향합니다.** 제가 놓쳤던 가드가 여럿 있었습니다.

- 미리보기(`action_scan`) → 적용(`action_apply`) 2단계이고, 적용 시점에 **번호가 그 사이 바뀌지 않았는지 재확인**합니다
- 적용 대상 중복, 변경 예정 번호 중복, 다른 저널의 번호 충돌을 각각 검사합니다
- 미리보기 단계에서도 "ready 였던 건이 blocked 로 바뀌면 그 번호는 다시 점유 상태로 본다"는 재귀 검사를 돌립니다
- `_check_account_manager()` 로 회계 관리자 권한을 요구합니다
- `current_rule` 이 `date_number` / `date_number_type` 가 아니면 아예 실행을 거부합니다

설계는 신중한 편입니다. **남는 것은 감사 추적 하나입니다.**

### 부수적으로 확인했고, 문제 아님

- `kr_sequence_repair_only_name` 이 core `_inverse_name()` 을 건너뜁니다. `_inverse_name()` 은 `payment_reference` 재계산과 `_set_next_made_sequence_gap(False)` 를 합니다.
  - `payment_reference` → core `_compute_payment_reference()` 는 `not m.payment_reference` 일 때만 채우므로, 어차피 기존 값을 덮지 않습니다. **영향 없음.**
  - `sequence_prefix` / `sequence_number` → `_compute_split_sequence` 로 `name` 에 의존하는 **저장 계산 필드**라 우회와 무관하게 갱신됩니다. **영향 없음.**
- `moves.write({"name": False})` 후 예외가 나면 트랜잭션이 롤백되므로 번호가 빈 채로 남지 않습니다. **영향 없음.**

## 5. 제안

번호를 바꾸는 기능 자체는 유지하되, **바꿨다는 사실을 남깁니다.** 셋 중 하나면 충분합니다.

**(A) 추적 비활성화를 `name` 한정으로 푼다** — 가장 작은 변경

Odoo core 의 `account.move.name` 은 이미 **`tracking=True`** 입니다 (`addons/account/models/account_move.py:127-133`). 즉 이 위저드가 `tracking_disable` 을 걸지 않았다면 chatter 에 "Number: 구값 → 신값" 이 **자동으로 남았을 것**입니다. 지금은 그것을 꺼서 안 남는 상태입니다.

두 키를 빼고 알림만 억제하면(예: `mail_auto_subscribe_no_notify`) 별도 코드 없이 이력이 복구됩니다. 다만 대량 건에서 chatter 쓰기 부담이 있으니, 건수가 크면 (B) 를 권합니다.

**(B) 영구 로그 모델을 둔다** — 권장

```
account.kr.move.sequence.repair.log  (models.Model)
  move_id, old_name, new_name, issue_type, user_id, date, wizard_batch
```
적용 시 한 줄씩 남깁니다. TransientModel 인 line 과 달리 사라지지 않고, 나중에 "이 번호는 왜 이렇게 됐나"를 역추적할 수 있습니다. IATF 심사·회계 감사 대응 시 그대로 증빙이 됩니다.

**(C) 전표에 메시지 한 줄을 직접 남긴다** — 중간

```python
move.message_post(body=_("전표번호 소급 변경: %s → %s", old, new))
```
`tracking_disable` 은 그대로 두고 `message_post` 만 명시 호출합니다. 성능 부담이 작고 chatter 에 남습니다.

### 함께 검토

- 적용 전 확인 창에 **"전기 완료된 전표의 번호를 변경합니다. 이미 발행·신고된 증빙과 어긋날 수 있습니다."** 경고를 넣는 것
- `restrict_mode_hash_table` / 잠금일이 **모두 꺼져 있을 때** 그 사실을 미리보기 화면에 표시하는 것 (지금은 가드가 없다는 걸 사용자가 알 수 없음)

## 6. 이 건과 PR #27 의 관계

**PR #27 의 머지 조건이 아닙니다.** `account_kr_plus_patch` 모듈 전체가 escon 정본에서 wilcoco 로 그대로 넘어오는 것이라, 이 코드는 PR 이전부터 있던 것입니다. #27 은 이 파일을 8줄만 건드렸고(`current_rule` 을 related → compute 로), 위 두 줄은 손대지 않았습니다.

정본(`escon-odoo/odoo_gh`) 쪽 별건으로 처리하는 것이 맞습니다.
