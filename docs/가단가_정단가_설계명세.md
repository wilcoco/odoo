# 가단가→정단가(소급 재정산) 설계명세 — 정산 세션 인계용

작성: 2026-07-03. 상태: **분석·설계(인계), 구현 전.**
구현 주체: **정산 세션**(gh_vendor_settlement, gh_transaction_statement 소유). 본 문서는 원가 세션이 작성한 인계 명세.
연계: [실제원가_관리분석_설계.md](실제원가_관리분석_설계.md) — 소급차이(retro_diff)·마감본 불변 원칙과 정합.

## 0. 배경·목적
자동차 양산 관행상 **양산 전 상당 기간이 가단가(임시단가) 거래**이고, 후에 **정단가가 확정되면 가단가 기간 차액을 소급 정산**해야 한다(매입·매출 양쪽). 현재 시스템은 이 "가/정 상태"와 "소급"을 구조적으로 모른다.

## 1. 현 구조 진단 (실코드 기준)
| | 매입 | 매출 |
|---|---|---|
| 단가 마스터 | `vendor.part.price` (품목+공급사+단가+**유효기간 from/to**) | **없음** ⚠ |
| 정산 grain | `vendor.mrp.accrual` (MO단위, 단가=계약단가→표준 폴백) | `transaction.statement` (명세) |
| 단가 정본 | 계약단가 마스터 | **`product.lst_price` 단일 현재값** ⚠ (수주라인 있으면 그 값, 없으면 lst_price 폴백) |
| 발행문서 단가이력 | in_invoice 라인에 보존 | out 세금계산서/명세 라인에 보존 |

## 2. 갭 (심각도 순)
| # | 갭 | 매입 | 매출 |
|---|---|---|---|
| G1 | **가/정 상태 개념 부재** — 단가가 임시인지 확정인지 시스템이 모름 | ⚠ | ⚠ |
| G2 | **매출 단가 마스터(상태·이력) 부재** — 정본이 lst_price 단일 현재값. 정단가 확정 때 이 값을 바꾸면 신규거래 구동·상태판정 근거 소실 | 양호(유효기간 有) | 🔴 |
| G3 | **소급 재정산 자동화 없음** — 정단가 확정 시 가단가 기간 차액을 아무도 계산 안 함 | ⚠ | ⚠ |
| G4 | **가단가 노출(exposure) 가시성 제로** — 지금 매출·매입 중 얼마가 가단가로 잡혀 있고 정단가 확정 시 얼마가 뒤집힐지 모름. 가단가 마진으로 의사결정 중 | ⚠ | ⚠ |

### ★ G2 정정 (원가 세션 검토 결과)
원분석의 "과거에 얼마로 팔았는지 **재현 불가/소급 원천 불능**"은 **과함**. **발행된 세금계산서·명세 라인(account.move.line)이 판매단가(price_unit)를 이력으로 보존**하므로 과거 단가·소급 차액은 **발행문서(accrual/명세 grain)에서 계산 가능**하다(원분석 본문도 이 방식으로 집계한다고 함).
→ 진짜 갭은 **"상태를 아는 전방(前方) 마스터의 부재"**: ①현재 가/정 상태 판정 ②신규거래 단가 구동 ③노출 가시성. **소급 원천은 이미 있으므로 G3는 생각보다 쉽다**(발행문서에서 delta 집계).

## 3. 개선안 — 매입 패턴을 매출에 대칭 복제 + 상태 추가
### ① 단가 마스터 대칭화
- **매입**: `vendor.part.price`에 `price_status`(가단가/정단가) + 근거(`agreement_ref` 합의서번호·`confirm_date` 확정일) 추가.
- **매출**: **`customer.part.price` 신설** — vendor.part.price의 미러(품목+고객+단가+유효기간+상태+근거). 명세·수주 라인이 lst_price 대신 이걸 조회, 없으면 **lst_price 폴백 + 단가출처 표시**(원가 세션의 PLC provenance 패턴 재사용: source/reason 필드).

### ② 가단가 라이프사이클 + 소급 재정산 액션 (매입·매출 동일 로직)
```
가단가 등록(status=가) → 거래 진행(명세·청구서 라인에 단가상태 낙인)
→ 정단가 확정(유효기간 소급 포함 신규행, status=정)
→ [소급 재정산] delta = (정단가 − 가단가) × 기거래 수량   ※ accrual/명세 grain에서 자동 집계(발행문서가 원천)
     매입 → 추가청구/감액 vendor bill 초안
     매출 → 수정 세금계산서 / credit note 초안
→ 승인 후 전기 (계산=자동, 전기=승인)
```

### ③ 가단가 노출 리포트 (경영 리스크 뷰) — G4
품목×거래처별 **"가단가로 발행된 누계액 + 정단가 확정 시 예상 변동액"**. "이 고객 정단가 협상이 늦을수록 얼마가 물려 있나"가 보여야 함. (매입·매출 각각 + 합산 순노출)

## 4. ★ 빠진 제약 — 세무(수정세금계산서) (원가 세션 추가)
소급을 세금계산서로 돌릴 때 **부가가치세법 제약 준수 필수**:
- **수정세금계산서 발행 사유코드·기한·부가세 신고영향** 규칙을 따를 것(임의 발행 불가).
- **이미 신고된 과거 기간은 재개봉 금지 → 당기(당월) 반영**. ← [실제원가_관리분석_설계.md]의 소급차이 원칙과 **정확히 일치**. 마감본 불변 + 소급차이 라인.
- 매입 측 수정세금계산서 수취도 동일 취급.

## 5. ★ 원가 세션과의 정합 (직접 연결)
- **매입** 가단가→정단가 확정은 원가 관리모듈 `injection_costing`의 **`injection.cost.monthly.close.retro_diff`(소급차이)로 그대로 흘러든다** — 실제 재료단가가 계약단가라, 계약이 정단가로 확정되면 그 차액이 관리원가 월마감의 소급차이가 됨. **해당 필드는 이미 존재**(추가작업 없이 정합).
- **매출** 가/정은 **마진·매출에만 영향, 제품원가엔 무영향** — 구분 명시. (원가는 매입·투입 기준)
- 마감 원칙 공유: 과거마감 재개봉 없이 당월 소급차이 계상.

## 6. 구현 순서·주체
1. **G2 = `customer.part.price` 신설** (이력·상태 없으면 나머지 전부 불가) — G1 상태필드는 이때 같이 탑재(별도 phase 불필요).
2. **G3 소급 재정산 액션** — **매입부터**(마스터 이미 있음), 발행문서 grain에서 delta 집계, 세무제약 반영.
3. **G4 노출 리포트**.
4. 매출 측 라이프사이클·수정세금계산서 흐름.
- **주체 = 정산 세션**(gh_vendor_settlement·gh_transaction_statement). 원가 세션은 retro_diff 수취 지점만 정합 확인.

## 7. 미결 결정 (구현 전 확인)
- 가/정 상태 전이 승인선(누가 정단가 확정?).
- 소급 delta 계산의 수량 원천(정산 accrual vs 발행 청구서 라인) 확정.
- 매출 수정세금계산서 자동초안의 세무 사유코드 매핑.
- customer.part.price 중복/유효기간 overlap 제약(vendor.part.price의 `_check_no_overlap` 패턴 재사용).

### 7-1. ★ 해결 — overlap 제약이 소급행을 막는 문제 (IATF/SQ 세션 확인, 2026-07-04)
**제약 재설계 불필요.** `_check_no_overlap`은 `self.search()`로 겹침을 검사하는데 Odoo search는
기본으로 `active=False`를 제외함(모델에 active 필드 있음). 따라서:
- **"정단가 확정" 액션이 원자적으로**: ① 완전 대체되는 가단가 행 → `active=False` 보관
  (+`superseded_by_id` 링크로 감사추적) ② 부분 대체(중간일부터 정단가)면 가단가 행의
  `date_to`를 단축(split) ③ 정단가 행 삽입 — 세 조작 모두 기존 제약을 통과.
- `get_price`도 search 기반이라 보관행은 신규거래 단가 구동에서 자동 제외됨(정확한 동작).
- 과거 적용가의 감사 원천은 발행문서 라인(§2 G2 정정) + 보관행 이중 확보.
- 주의: 액션 밖에서 수동으로 행을 지우거나 archive하는 경로는 supersede 링크가 안 남으므로,
  가단가 행의 직접 unlink는 막고(확정 액션 경유 강제) 권고.

## 8. ★ 검증 기준 (IATF/SQ 세션 보완, 2026-07-04 — 구현 후 cams_sim에서)
> C3(load_criteria)·F1에서 두 번 확인된 결함 클래스가 "재실행 비멱등"이었음. 소급 재정산은
> 같은 위험이 금액으로 직결되므로 아래를 구현 완료 조건으로 요구.
1. **멱등(이중 계산 방지) — 최우선**: [소급 재정산] 재실행 시 이미 소급전표가 발행된 delta를
   다시 만들지 않을 것. 권장: accrual/명세 라인에 `retro_bill_id`(소급전표 링크) 낙인 →
   재실행 시 미낙인분만 집계. (전표↔원천 상호 추적 링크도 겸함)
2. **양방향**: 인상(추가청구)뿐 아니라 **인하(정단가<가단가 → credit note/감액)** 검증.
3. **부분 정산 경계**: 가단가 기간 중 일부만 청구된 상태에서 delta가 **기청구분에만** 걸리고,
   미청구분은 (재정산이 아니라) 신규 정산 시 정단가로 잡히는지 — 이중/누락 없음.
4. **소급전표 취소 후 재실행**: 초안 반려/삭제 시 낙인 해제되어 재집계 가능한지.
5. **정합 등식**: 원가 관리단가(restated) − 월마감(frozen) = `retro_diff` 총액 — 월 대사에서
   자동 검증(등식 불일치 = 어딘가 이중/누락).
6. **폴백 낙인 가시성**: price_source=lst_price 폴백 라인이 노출 리포트(G4)에서 구분되는지
   (폴백 단가로 발행된 매출은 가단가보다 더 위험한 미합의 거래).
7. **가단가 평가서 시나리오**: 가단가 100원×3개월(매입·매출 각) → 정단가 120원 소급 →
   delta=20×기거래수량, 품목·월별 정확 + 과거 마감 재개봉 없음 + 확정월 "소급차이" 별도 라인.

## 9. ★ 구현 완료 (2026-07-04) — 신규 모듈 `gh_provisional_pricing`
> 정정: "정산 세션"은 별도 세션이 아니었음(모든 Odoo 플러그인이 이 세션 범위). 인계가 아니라 **직접 구현**함.

**구현물** (escon/odoo_gh, PR `feat/provisional-pricing`, fix/settlement-review 스택):
- `provisional.price.mixin`: 가/정 상태·근거·확정일 + `_confirm_firm`(§7-1 archive+insert: 가단가 active=False 보관→정단가 삽입→superseded_by 링크, overlap 통과) + 가단가 직접 unlink 차단.
- `vendor.part.price` 확장: 상태 + `_create_retro_settlement`(매입 소급) + `billed_exposure`(§G4 노출).
- `customer.part.price` 신설: 매출 단가마스터(가/정·유효기간·overlap·get_price 폴백). **매출 소급전표(수정세금계산서)는 후속**(§4 세무 사유코드 매핑 필요).
- `vendor.mrp.accrual.retro_bill_id`(멱등 낙인, ondelete set null).
- 정단가 확정 위저드 + 메뉴(계약단가 가/정 / 고객 판매단가 / 가단가 노출).

## 10. ★ 독립 적대 점검 결과 (IATF/SQ 세션, 2026-07-04, cams_sim3·전체 롤백)
자체검증(§9) 주장 항목 재검 + 자체검증이 안 다룬 오용 공격. **통과 8 / 결함 2**:

**통과 (독립 재확인)**: §8-1 멱등(재실행 무증가) · §8-2 인하→in_refund(20×50=1,000 정확) ·
§8-3 draft 정산분 제외 · §8-7 금액정확(60×100×2=12,000) · double-confirm 차단(archive행 재확정
시 오류) · superseded행 unlink 차단 · overlap 제약 유효(활성 firm 기간 겹침 차단) · §7-1
archive+insert 동작. (§8-5 정합등식은 원가 세션 검증 수용 — 독립 재검 안 함)

**🔴 결함 P1 — 소급전표 '취소(cancel)' 경로에서 소급 유실**
- 재현: 소급 draft를 `button_cancel`(삭제 아님 — **UI의 표준 반려 경로**) → accrual의
  `retro_bill_id` 낙인이 유지됨 → 재실행해도 해당 delta 재발행 안 됨 = **소급액 영구 유실**.
- §8-4는 '삭제(unlink→set null)'만 검증해서 통과했던 것. cancel은 미커버.
- 권장: retro 수집 도메인을 `['|',('retro_bill_id','=',False),('retro_bill_id.state','=','cancel')]`
  로 확장 후 재낙인, 또는 소급전표 button_cancel 시 낙인 해제. 수정 후 §8-4에 cancel 케이스 추가.

**⚠ 결함 P2 — unlink 가드가 §7-1 권고보다 좁음**
- superseded 행만 삭제 차단. **미확정(미대체) 가단가 행은 청구 노출이 있어도 직접 삭제 허용**
  → 노출 리포트(G4)에서 그 행이 사라짐(발행문서 이력은 남으나 전방 마스터 소실).
