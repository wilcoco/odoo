# 컨설팅 권고사항 보완 계획

작성 2026-07-15 · 근거: 프로젝트 전체 리뷰(컨설턴트 관점)의 권고 6건 · 원칙: 기능 추가보다 반복 가능성(테스트·절차·계획)에 투자.

## 보완 1 — 자동화 테스트 + CI (최우선)

목표: "오늘 검증된 것이 내일 커밋에서 깨지면 자동으로 알게 한다."

할 일:
1. 기존 검증 스크립트를 Odoo 정식 테스트로 승격한다. 이미 시나리오·기대값·데이터 구성이 완성돼 있으므로 이식 작업이다. 승격 순서는 돈과 직결된 것부터: ①정산 동시성(이중 발행 방지) ②원가 대사 정합(실제−표준=차이 합) ③소급 멱등·양방향·반려 후 재발행 ④PLC 백필(시리얼 보존·멱등 ack·스캔 가드) ⑤계획 BOM 전개·배정(비사출 제외·경고 수집).
2. 각 모듈 tests/ 디렉터리에 TransactionCase로 작성, 데모 데이터 의존 없이 테스트가 스스로 마스터를 만든다(시뮬 스크립트의 setup 부분 재사용).
3. GitHub Actions 워크플로: PR·push 시 PostgreSQL 서비스 + Odoo 18 컨테이너로 `-i 대상모듈 --test-enable` 실행. escon-odoo/odoo_gh와 wilcoco/odoo 양쪽에 동일 구성.
4. 완료 기준: 위 5개 영역 테스트가 CI에서 녹색으로 돌고, 실패 시 머지가 차단된다.

담당: 테스트 이식은 우리(AI 세션) 주도, CI 저장소 설정은 저장소 소유자(개발자) 승인 필요.
예상 규모: 테스트 이식 2~3일 분량, CI 구성 반나절.

## 보완 2 — 머지 절차 정착

목표: "재작성 흡수"가 있어도 유실은 절차가 잡는다.

할 일:
1. 규칙 합의(개발자와): 기능 브랜치는 PR로 열고, 리뷰 없이 직접 main 반영(흡수)한 경우에도 **흡수 후 원브랜치 재머지 diff=0 확인**을 필수 절차로 한다(이번에 수동으로 했던 그 검증의 절차화).
2. 이를 자동화: main push 시 CI가 열린 feature 브랜치들을 시험 머지해 유실 심볼 스캔(핵심 심볼 목록은 통합후검토 프롬프트에 이미 있음)을 수행하고 결과를 코멘트로 남긴다.
3. 통합후검토 프롬프트(docs/통합후검토_프롬프트.md)를 "머지 후 표준 점검 절차"로 공식화 — 대규모 머지 때마다 독립 세션으로 1회 실행.
4. 완료 기준: 다음 대규모 머지 1회를 이 절차로 통과시키고, 절차 문서를 팀 규칙에 등재.

담당: 규칙 합의는 매니저(사용자), 자동화는 우리.

## 보완 3 — 데이터 볼륨·성능 계획

목표: 개당 시리얼 체계(단위 MO·lot·QC 대량 생성)가 1~2년 뒤 성능 문제로 돌아오지 않게 지금 설계한다.

할 일:
1. 증가율 실측: 운영 개시 후 첫 달 기준 일일 단위 MO·stock.lot·quality.check·production_record 생성 건수를 측정해 연간 전망치 산출.
2. 보존 정책 결정(경영·품질 합의 필요): 추적성 요구(IATF, 통상 생산 후 N년)에 맞춘 온라인 보존 기간과, 그 이후 아카이브 방식(별도 스키마/테이블 이관 또는 읽기전용 아카이브 DB).
3. 기술 조치 선반영: 대량 조회 경로(시리얼 검색, 기간별 실적, 원가 재집계)의 인덱스 점검, 원가 재집계의 기간 스코프 옵션(전체 재계산 대신 당월만) 추가.
4. 완료 기준: "N년 보존 + 아카이브 방식 + 인덱스 점검 결과"가 문서 한 장으로 확정.

담당: 실측·인덱스·스코프 옵션은 우리, 보존 연한은 품질·경영 결정.

## 보완 4 — 미결 협의 종결 (시스템 가치의 나머지 절반)

목표: 코드는 준비됐으니 데이터와 결정이 들어오게 한다.

할 일(각각 담당과 마감 지정):
1. 시리얼 구분코드 확정 — "장애 시 PLC 자체 채번 = 2인가 3인가" 한 줄. 담당: 개발자+PLC업체. 확정 즉시 백필 로직 정리는 우리.
2. 미들웨어 송신 규격 — 완료 신호에 실측중량(weight)과 원생산시각(produced_at) 포함. 담당: 미들웨어. 이게 안 오면 실제원가가 표준 폴백으로만 돈다는 점을 명시해 우선순위를 올린다.
3. 실값 입력 캠페인 — 사출기 호기코드(1자리, v4.1 필수)·형체력, 금형 요구 형체력·교체시간, capability 실측 cycle, 워크센터 시간당원가, 실제 계약단가·톤단가. 담당: 생산기술·구매·원가. 입력 화면과 가이드는 이미 있음(화면별 입력가이드).
4. 대기 머지 3건(po-price-contract-first, serial-scan-guard, ops-process) 반영 확인.
5. 완료 기준: 미결 목록이 0이 되고, 실제원가 화면의 PLC 커버리지가 실데이터에서 0%가 아닌 수치로 확인됨.

## 보완 5 — 운영 보안 수칙 (협력사 포털)

목표: 좋은 DMZ 설계에 운영 절차를 붙인다.

할 일:
1. 토큰 수명 정책: 협력사 토큰 유효기간(예: 6개월)과 재발급 절차, 퇴출 협력사 즉시 폐기 절차를 문서화. 필요 시 토큰 만료 필드·재발급 버튼 소규모 개발.
2. 접근 로그: 포털 라우트 접근 기록(협력사·IP·시각)을 남기고 월 1회 이상 이상 접근 점검 — 기존 api.log 패턴 재사용 가능.
3. 게이트웨이 요청 제한(rate limit)과 실패 반복 차단은 프록시(DMZ nginx) 설정으로 처리 — 설정 예시를 배포 문서에 추가.
4. 백업·복구: 운영 DB 일일 백업과 분기 1회 복구 리허설을 배포 문서의 체크리스트로 명문화.
5. 완료 기준: 수칙 문서 1장 + 토큰 만료 기능 반영 + 첫 복구 리허설 1회 완료.

## 보완 6 — 업그레이드 대비 (Odoo 19)

목표: 전환 결정 시점에 "며칠 걸릴지"를 아는 상태를 만든다.

할 일:
1. 커스텀 모듈 인벤토리에 모듈별 이관 난이도 표기: 코어 API 의존도(낮음: 순수 신설 모델 / 중간: _inherit 확장 / 높음: 코어 흐름 개입), Enterprise 의존 여부.
2. 위험 상위 3~5개 모듈(예: 코어 MO 흐름을 깊게 확장한 injection_worksite)에 대해 19 변경점 사전 조사 메모.
3. 보완 1의 테스트가 곧 업그레이드 안전망이 됨을 전제로, "19 전환 리허설 = 새 브랜치에서 -u + 전체 테스트 그린"으로 전환 절차를 정의.
4. 완료 기준: 난이도 표 + 전환 절차 1장. (실제 전환은 별도 프로젝트)

## 실행 순서 제안

1주차: 보완 1 착수(정산 동시성·원가 대사 테스트 먼저) + 보완 4의 확정 요청 발신(구분코드·미들웨어 규격) + 대기 머지 3건 확인.
2주차: 보완 1 완료·CI 가동 + 보완 2 규칙 합의·자동 유실 스캔.
3주차: 보완 3(실측·인덱스·보존정책 초안) + 보완 5(토큰 정책·로그).
4주차: 보완 4 실값 입력 캠페인 완료 확인(커버리지 실측) + 보완 6 문서.

우선순위의 논리: 보완 1이 다른 모든 보완의 보험이므로 가장 먼저, 보완 4는 외부 의존이라 기다리는 시간이 필요하므로 요청만 먼저 발신해 병렬로 진행한다.
