`docs/신호_개발세션_SQ대응_개발요청.md` 의 0-B절 우선순위대로 **1주차 범위를 구현·검증**했다.

### 1. 범위 (신규 모듈 없음 — `iatf_mold` 확장만)

| 요청서 항목 | 내용 | 모델 |

1-3 을 1주차로 앞당긴 이유: 기준값(세척 주기)만 넣고 실적 원장이 없으면
"기한 경과 판정" 을 검증할 대상 자체가 없다. 6줄 추가로 기준이 살아난다.

### 2. 새로 생긴 화면 — UAT 대상

**메뉴 2곳 (기존 금형 대장이 양쪽에 있는 관례를 따랐다):**
- `IATF 16949 › 금형/치공구 관리 › 시사출(T/O) 보고서`
- `IATF 16949 › 설비 및 금형 관리 › 시사출(T/O) 보고서`

**금형 대장 폼 변경:**
- 상단 스마트버튼 「시사출 N건」
- 경고 배너 2종: 관리기준 미비 / 합격 T/O 없이 사용 중
- 「관리기준」 그룹 (등급·주기 / 온도 상하한 — 온도는 사출·다이캐스팅에만 표시)
- 「세척 계획 대비 실적」 그룹 (최근 세척일 / 차기 세척 예정)
- 탭 「시사출(T/O) 이력」

**금형 대장 검색 필터 3종 — 이게 SQ 평가자에게 보여줄 '지속 모니터링' 화면이다:**
| 필터 | 잡히는 것 |
|---|---|
| 관리기준 미비 | 등급·주기·온도 상하한 중 빠진 게 있는 금형 (무엇이 빠졌는지 `미비 항목` 컬럼에 텍스트로) |
| 세척 기한 경과 | 최근 세척일 + 세척주기 < 오늘 |
| 시사출 누락 | 사용(active) 상태인데 합격·완료된 T/O 보고서가 하나도 없는 금형 |

### 3. ⚠️ UAT 시 반드시 안내할 것 — 화면이 비어 있는 게 정상이다

**데모·샘플 실적 레코드를 0건 넣었다.** SQ 채점 기준에 허위기재 시 다수미흡(25%)이
명시돼 있어, 없는 이행실적을 만들어 채우지 않았다. 추가한 `data/` 는 보고서 번호
시퀀스 1건뿐이다.

따라서 UAT 순서서는 **테스터가 직접 입력해서 확인하는 순서**로 써야 한다:
1. 금형 1건에 관리기준을 넣기 전 → '관리기준 미비' 필터에 잡히는지
2. 등급·주기·온도를 채운 뒤 → 필터에서 빠지는지
3. 세척 이력을 주기보다 오래 전 날짜로 완료 등록 → '세척 기한 경과' 에 잡히는지
4. 금형을 '사용' 으로 전환 → '시사출 누락' 에 잡히고 chatter 에 경고가 남는지
5. T/O 보고서 작성 → **작성 중(draft)이나 재수정 판정으로는 해소되지 않고,
   합격 + 완료라야 해소되는지** (여기가 오해하기 쉬운 지점)

### 4. 설계상 알아둘 규칙 (매뉴얼에 반영 권장)

- **주기·상하한이 0(미입력)이면 판정하지 않는다.** 0 을 기준으로 읽으면 기준을
  넣은 적 없는 금형이 전부 부적합으로 찍힌다. 온도 판정 결과는 합격/불합격 외에
  **'기준없음(no_spec)'** 세 번째 값이 있다.
- **계획(planned) 상태 세척은 실적이 아니다.** 완료(done) 건만 실적으로 센다.
- **지그·게이지는 온도 기준이 없어도 미비가 아니다.** 예열 대상이 아니기 때문.
- **시사출 보고서가 달린 금형은 삭제되지 않는다**(`ondelete=restrict`). 심사 증빙
  문서라 조용히 사라지면 안 된다. 금형은 삭제 말고 **폐기(disposed)** 상태로.
- **합격 T/O 없이 사용 전환을 막지는 않는다.** 대신 chatter 에 경고를 남긴다.
  막으면 급할 때 상태만 우회로 바꾸고 기록은 여전히 안 남는다.
- 같은 금형에 같은 차수의 T/O 보고서는 둘일 수 없다(DB 제약).
- T/O 보고서에 **온도 필드는 넣지 않았다.** 2주차 `iatf.mold.temp.log` 가 온도의
  유일한 원장이 된다 — 원장을 둘로 만들지 않기 위함.

### 5. 검증 결과

- **자동 테스트 19/19 통과** (`--test-tags /iatf_mold`, cams_stg 복제 DB)
  - 요청하신 3종을 두 기능 각각에 대해 넣었다: 정상 기록 생성 / 기한 경과 판정 /
    상하한 벗어난 값의 합부 판정
- **업그레이드 경로 통과**: 1.0.0 코드로 금형 3건·보전 2건을 먼저 넣고 `-u` →
  기존 데이터·타수 보존, 신규 저장 컬럼 13개 생성, NULL 백필 0건
- **적대적 검증 25/25 통과**: 뷰 6종 렌더, 메뉴 양쪽 배치, T/O 삭제 시 누락 판정이
  다시 켜지는지(값이 굳지 않는지), 세척 200일 전 실적 + 180일 주기 → 경과 판정과
  검색 필터 결과 일치, `sq_evaluation` EVIDENCE_MAP 무손상

### 6. 착수 전 확인 요청하신 2건 — 1주차를 막지 않았다

- **금형 관리등급(A/B/C) 체계**: 등급은 라벨로만 두고, 주기·상하한은 등급에서
  자동으로 끌어오지 않고 **금형별로 직접 지정**하게 했다. 사내 체계가 확정되면
  '등급 → 기본 주기' 매핑을 나중에 얹을 수 있다(기존 데이터 영향 없음).
- **분쇄·배합 공정 유무**: 3주차(SQ 1_10·3_4)에만 영향. 없으면 해당없음 처리되어
  20점이 빠지므로 개발 불필요 — 3주차 착수 전까지 알려주면 된다.

### 7. 곁가지 발견 (UAT 환경 주의)

`sq_evaluation` 모듈이 **배포본과 `cams_stg` 에는 설치돼 있는데 `origin/18.0` 에는
없다** — 미병합 브랜치 `feat/sq-evaluation` 에만 존재한다. 18.0 기준으로 환경을
재구성하면 SQ 평가 화면이 사라진다. UAT 환경을 새로 만들 때 주의.

요청서 1-2·1-4 구현·검증 완료. 1주차와 함께 UAT 문서·매뉴얼에 반영을 요청한다.

- UAT 문서에는 "PR #30·#31 배포 후 유효" 로 표기할 것.

### 1. 범위 (신규 모듈 없음 — `iatf_mold` 확장)

| 요청서 | 내용 | 모델 |

### 2. 새로 생긴 화면 — UAT 대상

**메뉴 (1주차와 같이 양쪽에 배치):**
- `IATF 16949 › 금형/치공구 관리 › 금형 점검` / `… › 예열/온도 측정 이력`

**금형 대장 추가분:** 스마트버튼 「점검 N건」「온도측정 N건」, '점검 기한 경과' 경고 배너,
「계획 대비 실적」 그룹(일상점검·세척·시사출 3열), 탭 「점검 이력」「예열/온도 이력」,
검색 필터 **'점검 기한 경과'** 추가 (1주차 3종 → 총 4종).

**모니터링 목록 (평가자에게 보여줄 화면):**
| 위치 | 필터 | 잡히는 것 |
|---|---|---|
| 금형 점검 | 미완료(판정 누락) | 항목 판정이 비어 있는 점검표 |
| 금형 점검 | 이상 있음 | 불량 항목이 있는 점검 |
| 온도 이력 | 기준 이탈 | 상·하한 벗어난 측정 |
| 온도 이력 | 기준 없음(판정 불가) | 마스터에 온도 기준이 없어 판정 못 한 측정 |
| 금형 대장 | 점검 기한 경과 | 최근 일상점검일 + 주기 < 오늘 |

### 3. ⚠️ UAT 순서서에 꼭 넣어야 할 동작 — 오해하기 쉬운 지점

1. **빈 점검표는 '양호' 가 아니라 '미완료' 이고, 완료 버튼이 거부된다.**
   항목을 하나도 넣지 않거나 판정을 비워두면 완료할 수 없다. (설비 일상점검은
   빈 표가 '양호' 로 집계되는데, 그 동작을 일부러 따라가지 않았다.)
2. **상·하한을 넣은 항목은 결과를 손으로 못 고친다.** 측정값에서 자동 판정되며,
   기준 밖 값에 '양호' 를 저장하려 하면 **오류 메시지와 함께 거부**된다.
   → 테스터가 "결과를 못 바꾼다"고 이슈를 올릴 수 있으니 매뉴얼에 의도된 동작임을 명시.
3. **측정값을 비워두면(0) 불량이 아니라 '미판정'** 이다. 그 상태로는 완료가 안 된다.
4. **상·하한이 없는 항목은 사람이 양호/불량을 직접 고른다**(정성 항목).
5. **온도 기준이 없는 금형의 측정은 '기준 없음'** 으로 남는다. '적합' 이 아니다.
6. **작성 중 점검표는 실적이 아니다.** 완료해야 '최근 점검일' 이 갱신된다.
7. **정기 점검은 일상점검 주기를 리셋하지 않는다.** 정기 점검을 했어도 일상점검
   기한은 그대로 경과 상태로 남는다.
8. **측정 부위(고정측/이동측)와 방식은 필수**다. 비우면 저장되지 않는다.

### 4. 데모·샘플 실적 0건 (1주차와 동일)

UAT 는 테스터가 직접 입력해 §3 의 8개 동작을 확인하는 순서로 작성하면 된다.

### 3. UAT 순서서에 꼭 넣어야 할 동작 — 오해하기 쉬운 지점

1. **화면이 비어 있는 게 정상이다.** 데모·샘플을 하나도 안 넣었다.
   점검 시트(관리기준)조차 넣지 않았다 — 회사가 정한 기준이 아니면 그것도 지어낸 것이기 때문.

2. **한 번도 점검하지 않은 시트도 「미실시 목록」에 뜬다.** 이게 의도다.
   최근 점검일이 없으면 **운용 시작일**부터 주기를 센다. 그렇게 안 하면 만들어 놓고
   한 번도 안 한 대상이 목록에서 영영 안 뜬다 — 가장 적발해야 할 대상이 새는 셈.
3. **상·하한이 있는 항목의 결과는 손으로 못 고친다.** 측정값 넣으면 자동 판정된다.

   의도된 동작임을 미리 안내할 것. (허위기재 = SQ 다수미흡 25%)
4. **점검일을 미래로 넣을 수 없다.** 미래로 기록하면 차기 예정일이 밀려 미실시 목록에서
   사라지므로 막았다.
5. **측정값 0 = 미기입**(불량 아님). 기준값 0 = 판정 안 함.
6. **정성 항목(상하한 없음)은 사람이 양호/불량을 고른다.** 자동 판정 안 함.
7. **항목이 하나도 없는 점검표는 '양호' 가 아니라 '미완료'** 이고 완료 처리가 거부된다.
   판정이 빈 항목이 하나라도 있으면 마찬가지.
8. **작성 중(draft)은 실적이 아니다.** 완료(done) 처리해야 최근 점검일이 갱신된다.
   완료를 취소하면 실적에서 다시 빠진다.
9. **시트 기준을 나중에 바꿔도 과거 실적은 그때 기준 그대로다.** 기준 항목을 삭제해도
   과거 실적 라인은 남는다. (심사 증빙이라 그렇게 해야 한다)
10. **보관(archive)한 시트는 미실시 목록에서 빠진다.** 운영 안 하는 대상을 미실시로
    쌓아 두지 않기 위함.

> 아직 안 지난 건이 한 목록에 섞여 나온다.** 실제로 감점되는 건 이미 지난 건인데

> 기존 필터는 동작을 바꾸지 않고 그대로 뒀다. **매뉴얼에는 두 필터의 차이를 써야 한다.**

### 3. UAT 순서서에 꼭 넣어야 할 동작 — 오해하기 쉬운 지점

1. **화면이 비어 있는 게 정상이다.** 1~3주차와 같다. 위험성평가·사고 이력 모두 0건이다.
   안전점검 시트 기준도 안 넣었다. §4 표를 보고 담당자가 직접 입력해야 화면이 산다.
2. **위험성 점수는 자동 계산이다.** 가능성(1~3) × 중대성(1~3).
   **4점 이상이면 '허용 불가'**, 3점 이하면 '허용 가능'. 사람이 못 고친다.
3. **허용 불가 항목에 감소대책이 비어 있으면 「평가 완료」가 거부된다.**
   위험만 적어 놓고 대책 없이 완료 처리하는 게 SQ 에서 가장 흔한 감점 사유라 막았다.
   테스터가 버그로 올릴 수 있으니 의도된 동작임을 미리 안내할 것.
4. **유해위험요인이 하나도 없는 평가서도 완료가 거부된다.** 빈 평가서가 '평가 완료 n건' 으로
   집계되면 그게 허위기재다.
5. **완료한 평가서의 요인 줄을 나중에 지워도 막힌다.** 완료 뒤에 내용만 비우는 우회 경로다.
   지우려면 먼저 「작성중으로」 되돌려야 한다.
6. **사고는 원인·재발방지대책·대책완료일이 다 있어야 「종결」된다.** 셋 중 하나라도 비면 거부.
   또 원인 분석 없이 「대책 이행」 단계로 건너뛸 수 없다.
7. **아차사고와 실제 사고를 같은 화면에 기록한다.** 「유형」으로만 구분한다.
   분리하면 "사고 0건" 숫자만 남고 예방활동 증빙이 사라진다 — 심사에서 아차사고 발굴 실적을 본다.
8. **발생일시·완료일을 미래로 넣을 수 없다.** 점검 일지와 같은 규칙.
9. **개선 후 위험성은 가능성·중대성을 둘 다 넣어야 점수가 나온다.** 하나만 넣으면 공란이다.
   (한쪽만 넣고 "개선됨" 으로 보이는 걸 막기 위함)
10. **안전점검은 새 화면에 만드는 게 아니다.** 점검 시트를 만들 때 「안전점검」을 체크하면
    안전관리 메뉴에도 뜬다. 체크 안 하면 일반 점검 목록에만 뜬다.
11. **미실시 내부심사 = 계획일이 지났는데 아직 '계획' 상태인 심사.** 계획일 **당일은 아직 아니다**.
    심사를 시작하면(실시일 기록) 목록에서 빠진다. 취소한 심사도 안 뜬다.
12. **「실적일 미기록」 필터**는 상태만 진행/보고로 바꿔 놓고 실제 실시일이 빈 건을 잡는다.
    계획 대비 실적이 SQ 6_4 의 핵심 증빙이라 따로 뒀다.

**(1) 위험성평가 — 사출 공정 기준 최소 골격.** 가능성·중대성 점수는 회사가 판단할 값이다.

### 5. 3주차(#32) 결함 2건 — #33 에서 수정

적대적 검증 중에 나왔다. 둘 다 **"완료 실적으로 집계되는데 내용은 비어 있는" 경로**다.

1. **상태를 직접 바꾸는 우회** — 완료 버튼의 검사는 버튼 경로에만 걸려 있었다.
   데이터 임포트·API 로 상태만 '완료' 로 쓰면 판정이 빈 점검표가 실적이 됐다.
   → 상태값 자체에 검사를 걸었다(버튼을 안 거쳐도 막힌다).
2. **완료 후 항목 줄 삭제** — 완료 처리한 뒤 항목을 전부 지우면 내용 없는 '완료' 가 남고,
   그게 최근 점검일로 잡혀 **미실시 목록에서 사라졌다.**
   → 줄 삭제 시 점검표를 다시 검사하게 했다.

같은 구멍을 새로 만든 위험성평가·사고 이력에도 미리 막아 뒀다.

### 3. UAT 순서서에 꼭 넣어야 할 동작 — 오해하기 쉬운 지점

1. **화면이 비어 있는 게 정상이다.** 1~4주차와 같다. 기준·분쇄·배합 전부 0건이다.
   **기준을 먼저 등록해야 배합일지가 판정된다.** 순서가 반대면 전부 「미판정」으로 쌓인다.
2. **분모를 시스템이 정하지 않는다.** 기준 등록 화면의 「비율 기준」에서 회사가 고른다.
   - **수지 기준** = 재생재 ÷ (신재+재생재) ← 보통 이쪽
   - **총 투입량 기준** = 재생재 ÷ (신재+재생재+첨가제)
   같은 배합도 분모에 따라 합부가 갈린다. **담당자에게 반드시 확인받아야 할 항목이다.**
3. **판정은 사람이 못 고친다.** 재생률·합부는 자동 계산이고 화면에서 읽기 전용이다.
   기준을 넘긴 배합에 '기준 이내' 를 적어 넣는 경로를 막아 뒀다(허위기재 = SQ 다수미흡 25%).
4. **기준이 없으면 「합격」이 아니라 「미판정」이다.** 그리고 **완료를 막지 않는다.**
   원인이 작업자가 못 고치는 마스터 공백이라, 막으면 현장이 기록 자체를 안 남긴다.
   대신 「기준 초과·판정불가 배합」 화면에 걸리게 했다. **이 화면이 5주차의 핵심 점검 화면이다.**
5. **재생재를 넣은 줄은 분쇄일지를 지정해야 완료된다.** 출처 없는 재생재는
   배합일지가 있어도 "어디서 온 재생재인지 모르는 상태"라 추적이 끊긴다.
6. **기준을 나중에 완화해도 과거 판정은 안 바뀐다.** 상한값을 배합일지에 복사해 두기 때문이다.
   (안 그러면 상한을 올리는 순간 과거의 초과 배합이 전부 합격으로 뒤집힌다)
7. **적용일이 미래인 기준은 안 쓴다.** 오늘 만든 기준으로 지난달 배합을 판정하지 않는다.
8. **분쇄일지의 산출량 > 투입량 이 거부된다.** 통과시키면 재생재 재고가 부풀고,
   그 숫자가 그대로 배합 비율의 분자가 된다.
9. **이미 배합에 쓰인 분쇄일지는 삭제되지 않는다.**
10. **배합일·분쇄일을 미래로 못 넣는다.**

### 4. 담당자가 넣어야 할 입력 (기준부터)

「배합 관리기준」에 **품목별로 최소 1건**. 없으면 전부 미판정이다.

| 품목 | 재생재 상한(%) | 비율 기준 | 첨가제 상한(%) | 적용일 | 고객승인 |
|---|---|---|---|---|---|
| (사출품마다) | 예: 20 | 수지 기준 | 예: 5 | 가동 개시일 | 승인서 있으면 문서번호·승인일 |

### 1. 무엇을 고쳤나 — 레거시 3대 문제

| # | 레거시(현행 공장) | 새 구조 |
|---|---|---|
| ① | 분류 코드 SPMSRT **4자리 한 칸**에 4계층을 눌러 담음 (`AIAA` = 생산기술:사출:사출성형기:UBE-2200T) | `iatf.spare.category` 를 진짜 트리로. 코드는 **자리별로** 저장하고, 레거시와 같은 모양 `AIAA` 는 「전체 코드」가 이어붙여 보여준다. **상위 자리를 고치면 하위 전체가 따라 움직인다** (레거시는 하위 행을 전부 다시 써야 했음) |
| ② | 잎(부품 달리는 기종)과 가지(`A000`, `AA00` 같은 묶음)가 같은 표에 섞임. 코드 60개 중 42개에만 부품 | 부품은 **기종 노드에만** 달린다. 묶음 노드는 부품을 받지 못한다. 「부품이 없는 기종」 필터로 빈 잎과 묶음을 구분해 본다 |
| ③ | 분류가 1:N 강제 — 같은 베어링이 설비 10대에 쓰이면 **부품 행이 10개**, 재고를 10번 따로 봄 | `iatf.spare.application` **적용표(다대다)** 신설. 부품 마스터는 한 행, 어느 설비에 들어가는지는 적용표가 여러 줄로 적는다 |

추가로 레거시는 **설비 분류(MCHSRT 2자리)와 부품 분류(SPMSRT 4자리)가 겹치는 코드 0건**이라
"이 설비에 맞는 부품"을 시스템이 알 방법이 없었다. 실물 설비에 **「기종」** 을 지정하게 하고
「기종 부품 일괄 적용」 버튼으로 그 기종의 부품을 한 번에 가져온다.

**분류와 적용은 대체 관계가 아니라 둘 다 필요하다.**
- 분류 = "이 부품이 **어디에 속하는가**" — 한 자리
- 적용 = "이 부품이 **어디어디에 들어가는가**" — 여러 개

### 2. 메뉴 경로

- 설비관리 ▸ **예비부품 분류** — 부문/공정/설비군/기종 트리 등록
- 설비관리 ▸ **부품 적용표** — 부품↔설비 연결을 한 화면에서 관리
- 설비관리 ▸ 예비부품 — (기존) 목록이 「설비별」에서 **「분류별」** 그룹으로 바뀜
- 설비 대장 ▸ 설비 폼 ▸ 식별 그룹에 **「기종」** 필드 추가, 「예비부품」 탭에 일괄 적용 버튼

### 3. UAT 주의사항

1. **분류 데이터를 깔아 두지 않았다.** 회사 실제 체계와 다른 트리가 증빙에 섞이면
   안 되므로 데모 분류 0건이다. 첫 화면은 비어 있는 게 정상이다.
2. 코드는 **자리 하나만** 넣는다. `AIAA` 를 통째로 넣지 말 것 — 「전체 코드」가 자동 조립한다.
3. 등록 순서는 반드시 **부문 → 공정 → 설비군 → 기종**. 건너뛰거나 거꾸로면 저장이 거부된다.
4. 같은 상위 아래에서만 자리 코드가 유일하면 된다. `A` 는 자리마다 다른 뜻이므로
   부모가 다르면 같은 `A` 를 써도 된다 (전역 유일이면 트리를 못 만든다).
5. 부품은 **기종**에만 달린다. 묶음 노드를 고르면 저장이 거부된다.
6. 부품이 달린 기종은 (a) 하위 분류를 만들 수 없고 (b) 계층을 올릴 수 없다.
   먼저 부품을 다른 기종으로 옮겨야 한다.
7. 설비의 「기종」은 최하위(기종) 노드만 지정된다. 설비군을 넣으면 저장이 거부된다.
8. 「기종 부품 일괄 적용」은 **두 번 눌러도 중복이 생기지 않는다.** 이미 있는 건 건너뛴다.
9. 여러 설비를 선택해 일괄 적용할 때 **기종이 안 잡힌 설비가 하나라도 섞이면 전체가 거부**된다.
   일부만 적용되고 나머지는 조용히 빠지는 상황을 막기 위해서다.
10. 「최소 보유 기준」(부품 마스터)과 「설비 1대당 소요」(적용표)는 **다른 값**이다.
    전자는 창고 재고 기준선, 후자는 설비 한 대에 들어가는 개수다.

### 4. 담당자 입력이 필요한 것

- **분류 트리 자체.** 우리 새 공장의 부문/공정/설비군/기종을 정해서 넣어야 한다.
  레거시 60개 코드를 그대로 옮길 필요는 없다 (기존 공장 건이고, 데이터도 안 넘어온다).

`iatf_equipment` 에 드리프트가 있으면 **동기화 전에 먼저 정본으로 끌어올린다.**

**③ 미러 반영 → 서버 pull**
```bash
# odoo_gh/iatf_plugins/iatf_equipment 를 정본 addons_custom/iatf_equipment 로 동기화 후 push
scripts/mirror_diff.sh --module iatf_equipment    # 동기화 후: diff 0 을 확인
# 서버에서
cd <서버 odoo_gh 경로> && git pull
```

**④ 업그레이드 — 마이그레이션이 여기서 돈다**

④⑤ 는 `scripts/deploy_iatf_equipment.sh` 한 줄로 대체되었다 (백업·pull·업그레이드·
검증·재기동을 순서대로 하고, 어긋나면 **재기동 전에 멈춘다**). 서버에서:
```bash
cd ~/cams-odoo && bash scripts/deploy_iatf_equipment.sh 2>&1 | tee ~/deploy_result.txt
```
> `scripts/` 는 어느 repo 에도 커밋돼 있지 않다(untracked). 서버가 `git pull` 해도
> 딸려오지 않으므로 **파일을 따로 전달**해야 한다.

> ⚠️ **운영 DB 명이 문서마다 엇갈린다.** UAT·사용자 매뉴얼 여러 건은 `odoo18`
> (단일 DB)이라 하고, `odoo.conf` 주석에는 `^cams$` 가 있다. `cams`/`cams_stg` 는
> 로컬 검증용 이름이다. 틀린 DB 에 `-u` 를 때리면 엉뚱한 DB 의 스키마가 바뀌므로,
> 스크립트는 **추측하지 않고** 서버의 DB 를 세어 하나면 그것을 쓰고 여럿이면 멈춘다.
> 여러 개일 때: `DB=<운영DB명> bash scripts/deploy_iatf_equipment.sh`

아래는 스크립트가 대신 실행하는 내용이다 (수동으로 할 경우의 원본):
```bash
docker compose exec odoo bash -lc \
  'python3 /mnt/odoo/odoo-bin -c /etc/odoo/odoo.conf -d <운영DB> \
   -u iatf_equipment --stop-after-init --db_password=$DB_PASSWORD'
```
로그에 **두 줄 다** 보여야 성공이다 (서버가 1.0.0 에서 출발하므로 마이그레이션이 2개 돈다):
```
module iatf_equipment: Running upgrade [18.0.1.1.0>] post-migration
module iatf_equipment: Running upgrade [18.0.1.3.0>] post-migration
```
**한 줄이라도 없으면 멈추고 알려 달라.** 1.3.0 이 안 돌면 잔재 컬럼(NOT NULL)이 남아
예비부품 신규 등록이 실패하고, 1.1.0 이 안 돌면 「가동시간 없으면 가동률 100%」라는
옛 계산 결과가 컬럼에 남아 SQL 리포트가 거짓값을 읽는다.

업그레이드 뒤 확인 쿼리:
```sql
-- 잔재 컬럼이 전부 사라졌는지 (3행 모두 0 이어야 함)
SELECT count(*) FROM information_schema.columns
 WHERE table_name='iatf_equipment_spare' AND column_name='equipment_id';
SELECT count(*) FROM information_schema.columns
 WHERE table_name='iatf_equipment' AND column_name IN ('mtbf','availability_rate');
-- 기존 부품↔설비 연결이 적용표로 옮겨졌는지 (업그레이드 전 부품 건수와 같아야 함)
SELECT count(*) FROM iatf_spare_application;
```

**⑤ 재기동 + 확인**
```bash
docker compose restart odoo
```
- 설비관리 메뉴에 「예비부품 분류」·「부품 적용표」가 보이는지
- 예비부품 목록에서 「설비」 열이 사라지고 「분류」·「적용 설비」가 보이는지
- 예비부품을 **새로 하나 등록**해 보기 (④가 제대로 돌았는지 확인하는 가장 빠른 방법)
- (1.1.0 동반분) 설비 폼에 **「계층 구분」**(공장/라인/설비/장치)·「상위 설비」가 보이는지.
  기존 설비는 전부 「설비」로 채워진다 — 라인·공장을 쓰려면 나중에 손으로 올린다
- (1.2.0 동반분) 예비부품 폼에 「품목」·「수량 출처」가 보이는지. **기존 부품은
  「미집계」로 뜨는 게 정상**이다 (품목 미연결 + 수기값 없음). 0 은 「0개」가 아니라 「모름」

**되돌리기**: 코드는 미러를 이전 커밋으로 되돌리면 되지만, **④의 컬럼 DROP 은
자동으로 되돌아가지 않는다.** 되돌릴 일이 생기면 DB 백업에서 복구해야 하므로
④ 직전에 `pg_dump` 를 받아 둘 것.

### 8. 확인 대기

1. **분류 트리 초안**을 누가 만들 것인가. 새 공장 설비 목록이 나와야 시작할 수 있다.
2. 「최소 보유 기준」을 부품 마스터에 두는 게 맞는가, 아니면 **설비 대수 × 1대당 소요**로

   근거 없는 숫자를 만들지 않기 위해).
3. 예비부품 **발주**는 아직 미구현이다. 붙일 때는 `injection_planning` /

   만들면 이중 발주가 된다).

## [회신 2026-09-04] 점검 양식 프레임 — 항목·단위·기준·주기를 화면에서 고칠 수 있게

브랜치: `feat/iatf-check-sheet-frame` (`46d2cf70ffa`) · 모듈 `iatf_work_environment` 18.0.1.3.0
분기점: `feat/iatf-blend-log` 위 (프레임 원본이 그 스택에 있어 18.0 에서 딸 수 없다)

### 0. 왜 했나

회사 실제 양식(`'24년도 설비 일상점검표`, 시트 22장)을 확인한 결과, 항목 구성이
공정·설비마다 전부 다르다. 양식을 코드에 박으면 설비가 하나 늘 때마다 개발이 필요하다.
그래서 **정의(무엇을·어떤 단위로·어떤 기준으로·얼마나 자주)를 데이터로** 옮겼다.

### 1. 항목 정의에 생긴 것

| 필드 | 무엇 | 회사 양식 근거 |
|---|---|---|
| 입력 방식 | 양호·불량 / 수치 기입 / 내용 기입 | 점검표의 '방법' 열(육안·수치기입·시연) |
| 기준 방식 | 정성 / 범위 / 하한 이상 / 상한 이하 / **목표±공차** | 사출 작동유 `40℃±10℃`, 조립 AIR `0.4~0.6Mpa` |
| 항목 주기 | 비우면 시트 주기, 채우면 그 항목만 별도 | 도장 믹싱룸 시트의 항목별 주기 열 |
| 중요 관리 항목 | 미실시 집계에서 먼저 보임 | 모든 시트 하단 `※ 금월 중요 관리 항목` |

기준 방식은 **표기**일 뿐이고, 판정은 상·하한 한 갈래로만 돈다(목표±공차는 상·하한으로
환산해 저장). 판정 로직이 갈라지지 않게 하기 위해서다.

### 2. 개정해도 과거 판정이 흔들리지 않는다 — 이번 작업의 핵심

기준을 화면에서 고칠 수 있게 만드는 순간, **과거 실적의 판정 근거가 소급해 바뀌는 길**이
열린다. `40±10` 에서 합격이던 47℃ 가, 기준을 `40±5` 로 좁힌 뒤 화면에서 불합격으로 보이면
심사에서 "이 값이 왜 합격이었나" 에 답할 수 없다. 판정 기록을 변조하는 시스템이 된다.

막은 방법 세 가지:
1. 실적 라인이 **판정 당시 기준을 복사**해 들고 있다(기존 구조를 확장)
2. 실적에 **몇 차 개정본으로 점검했는지** 를 남긴다
3. 개정 이력은 **관리자도 수정·삭제할 수 없다**(ACL read-only, 생성은 sudo 경로만)

부수 효과로 개정 이력 자체가 SQ 1_1(표준류 일치성)·IATF 문서관리 증빙이 된다.

### 3. 조용히 망가지는 경로 3개 (막음)

| 경로 | 왜 나쁜가 |
|---|---|
| 상·하한만 주고 기준 방식을 안 줌 | 기본값 '정성' 이 되어 기준이 화면에는 보이는데 판정에 안 쓰인다. **기준이 없는 것보다 나쁘다** — 담당자는 걸려 있다고 믿는다 |
| 방식과 어긋난 경계값 | 조용히 0 으로 지우면 원인을 못 찾는다. 지우지 않고 이유를 말하고 막는다 |
| 수치 기준 + 양호·불량 입력 | 측정값 칸이 없어 눈대중 판정이 된다. 기준이 장식이 되는 상태가 SQ '보완(60%)' 사유 |

### 4. 검증

- **테스트 70건 통과** (프레임분 14건 신규 — 정상 기록 / 기한 경과(항목별 주기) / 상하한 합부 3종 포함)
- **기존 DB 업그레이드 경로**: `blend1`(18.0.1.2.0) 복제 → 레거시 행(시트 1·항목 2·완료 실적 1) SQL 로 심기 → 1.3.0 업그레이드

> **1차 검증에서 마이그레이션 결함 1건이 실제로 잡혔다.** 실적 라인이 이관되지 않았다.

> 로는 "기본값이 박힌 상태" 를 못 잡는다. 새 DB 설치로는 안 보이고 기존 DB 업그레이드에서만 난다.
