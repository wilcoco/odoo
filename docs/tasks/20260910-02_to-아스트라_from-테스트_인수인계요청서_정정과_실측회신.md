## 4. 통합시험 환경 설계에 반영할 제약 (요청서 미반영)

1. **UAT 를 운영 DB 에서 진행 중**입니다. DB 가 1개라 테스트 발주·전표가 **실번호를 소비**합니다.
   → §5-3 "검증 DB" 는 운영과 분리하려면 **덤프 복원본**이어야 합니다.
2. **양산 개시 전**이라 이행실적이 없습니다 → 기대값을 과거 실적으로 잡을 수 없습니다.
3. **데모 데이터로 실적을 채우면 안 됩니다** — SQ 채점에 "허위기재 시 다수미흡(25%)" 명시.

## 5. §6 최소 합격 기준 추가 제안 3건 (실제 사고 유형)

1. **테스트가 실행됐는지 확인** — 환경 조건(계정과목표 미로드) 때문에 테스트가
   **조용히 skip 되며 통과로 보이던** 사례가 있었습니다. 합격 판정 시 skip 수 동반 보고.
2. **핵심 회귀는 사보타주 검증** — 고친 코드를 되돌렸을 때 그 테스트가 실제로 실패하는지 확인.
3. **기존 DB 업그레이드 검증** — Odoo 가 새 컬럼을 기본값으로 먼저 채우므로
   `COALESCE(NULL)` 검사로는 "기본값이 박힌 상태" 를 못 걸러 실적 라인 이관이 누락된 사례.

## 6. 함께 보고 — 지적받은 결함 수정 완료

세금계산서 파일 반입의 **행 단위 롤백 누락** 지적("생성 0건인데 초안 청구서가 남는다")은
수정했습니다. 행 생성을 `cr.savepoint()` 로 감싸고 세이브포인트 **안에서** `flush_recordset()`
을 호출해 지연 제약이 그 안에서 터지게 했고, 자동 게시도 건별로 격리했습니다.
회귀 테스트를 붙인 뒤 **세이브포인트를 제거하면 실제로 실패하는 것까지 확인**했습니다.
브랜치 `feat/tax-invoice-file-import` (`ce025d5`) — 머지 대기.

## 7. 아직 회신 못 하는 것 (담당 지정 필요)

운영 `addons_path` 실제 값·경로별 SHA, 운영 PG 버전·백업/복원 절차, 운영 재고 평가 방식,
go_relay·MQTT 실제 메시지 예시, 대표 범퍼 BOM·LOT 규칙·손실률, CSR 적용 버전.
→ 서버·MES·현장/품질 담당 회신이 필요합니다.
