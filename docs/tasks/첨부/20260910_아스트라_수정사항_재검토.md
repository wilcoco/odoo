검토자: 아스트라 · 2026-09-10 · 사용자 승인: “어 검토해..”

**판정: 수정 효과는 확인됐지만, 이번 제출분을 전체 해결로 인수하기에는 보완이 필요하다.** 청구서 생성·게시 롤백, 금형 미래일 차단, 신규 온도 기록의 마스터 단독 개정 보호, SPC 입력 표본 계산, PPAP 회사별 검색은 개선됐다. 그러나 일반 담당자 권한에서 완료 점검 기록과 판정을 바꿀 수 있고, SPC 측정 누락·덮어쓰기 및 음수 세금계산서 부가세 누락이 재현됐다.

## 4. 시험 결과를 읽는 방법

별도 내부 Docker 네트워크와 메모리 기반 PostgreSQL17 DB `codex_review2`를 새로 만들었다. 제품 소스는 고정 스냅샷을 읽기 전용으로 마운트했다. 품질 `7d6dc8b`에 회계 모듈 `c9ad89d`를 우선 적용한 조합이며 운영 DB 복제본은 사용하지 않았다.

- 런타임: 설치되어 있던 이미지 `cams-odoo:18.0-oracle`, 이미지 SHA `876e3deab74a5e24e60ef03d159c1f1bcdd064652690ba0667abf1e219864d9e`, 내장 Odoo `18.0-20260609`.
- 최초 회귀: **180개 시험 메서드, 실패0·오류0·건너뜀7**. 이 중 한국 세목 미로드6건, MES `injection_worksite` 미설치1건.
- 한국 회계 모듈 설치 후 관련 두 클래스 재실행: **8개 메서드, 실패0·오류0·건너뜀0**. 앞서 건너뛴 회계6건 포함.
- 중복 실행을 빼면 **고유179건 통과, 1건 건너뜀**. 남은1건은 단위 MO 집계로 MES 모듈을 포함한 통합 환경에서 확인해야 한다. PPAP 모듈에는 이 대상 신규 시험 클래스가 없어 별도 ORM 사례로 검증했다.
- 독립 동작 확인: 금형·점검12개 관찰, 그중 주요 경로 권한별 재확인7개, SPC·회사6개, 회계7개. 이것은 제품 회귀 통과 건수에 더하지 않는다. 결함이 재현된 관찰도 포함한다.
- 회계의 create/flush/post 오류는 **실제 ORM 동작 이후** 시험용 예외를 주입했다. 정상 건의 생성·게시 보존과 실패 건의 롤백을 PostgreSQL에서 확인했다.
- 처음 회사·회계 probe의 설정 부족은 별도 로그로 보존했다. 표준 창고·시퀀스와 신규 KR회사·차트를 준비해 재실행했으며 설정 오류를 제품 결함으로 세지 않았다.
- 변경된 Python/XML 24개 파일 구문 검사 완료. `CLAUDE.md`를 포함한 품질 diff는 25파일 +477/-85다.

제출 로그의 **156과 모듈 통계 합계180 차이**는 준비·정리(setUpClass/tearDownClass)를 통계에 포함하는 Odoo 구현으로 설명된다. 12개 클래스의 준비·정리24를 더하면180이다. 숫자 차이 자체를 시험 오류로 보지 않는다. 다만 제출본은 필터링된 로그여서 skip0 여부·실제 마운트 소스까지 단독으로 입증하지 못한다. 최신 회신은 codex2인데 판정 문서에는 codex1과 이전 파일 수가 남아 있어 문서 정합화가 필요하다.

이번 결과는 고정 커스텀 소스와 위 런타임의 시험 결과다. 실제 배포 코어·Enterprise·MES 전체 조합, 기존 데이터 이관, 동시 처리, 바코드·PLC·현물 및 사용자 화면 검증을 완료했다는 뜻은 아니다.

## 5. 테스트 측 인수인계 회신에서 정정할 내용

- “18.0이 이전 점검 이후 이동했다”는 문구는 이번 원격 조회값과 맞지 않는다. 확인 시각과 전체 SHA를 기준으로 기록해야 한다.
- 직접 하위 폴더의 `__manifest__.py`를 기준으로 세면 **ERP53개·ERP 미러60개·MES28개**다. 폴더·문서·설정 파일 수를 모듈 수와 혼용한 55/66/31은 인수 목록으로 그대로 쓰기 어렵다.
- 공통 ERP53개 중 **50개 동일, 3개 차이**는 확인됐다: `escon_mainmenu`, `pumui_approval`, `supplier_portal_purchase`. 미러 전용7개도 확인됐다. 비교 MES 기준은 기존 고정 로컬 `49002743a7243948bdc098cef77e7f2f8386fef8`이며 원격 최신성·운영 배포를 뜻하지 않는다.
- 서버 담당의 기존 회신 자료는 이미 있다. “자료 미수신”과 “제출 자료 수신·독립 운영 검증 미실시”를 구분해야 한다.
- 완료 기록을 더 이상 고칠 수 있다는/없다는 선언, PQC 회사 명시 “2곳”, migration 완료 표기는 이번 실제 코드·재현 결과에 맞춰 좁혀야 한다. 이번 diff의 PQC 회사 추가는 단위 MO 분기1곳이다.
- 기존 인수인계 산출물은 덮어쓰지 않고 이 정정표를 추가했다. 출처를 추적할 수 있도록 기존 제출 자료를 함께 보존했다.

## 6. 운영 준비도와 다음 협의안

사용자는 공장 가동 전임을 전제로 **“지금 운영한다면 전체 흐름이 가능한가”**를 물었다. 따라서 원 보고서의 양산 전 보완 권고는 현재 공장이 가동 중이라는 전제와 무관하다. 명칭은 “양산 전 필수 보완·인수 조건”으로 통일하면 혼동을 줄일 수 있다.

이번 패치는 전체 통합 인수의 일부다. 기존 H01 이종검사 진행 차단, H02 가상 LOT와 실재고 분리, H03 OQC 보류·범위·롤백, 계획 중복·ASN/PO·IQC·BR/JIT·정산 문제는 이번 제출로 해결되지 않았다. 특히 SQ/IATF의 안정적인 운영을 위해서는 완료 품질 증빙 보존과 불합격·미검사 상태의 다음 공정/출하 차단을 함께 확인해야 한다. 이 검토만으로 SQ 평가 통과나 IATF 인증 적합을 판정하지 않는다.

권하는 다음 순서는 다음과 같다. **아직 배정·수정 실행하지 않은 협의안이다.**

1. 이번 인수 판정을 “부분해결”로 공유하고, 증빙 변경 R01~R03 및 회계 R10을 먼저 보완한다. SPC 신규 회귀 R05~R06도 같은 수정 묶음에서 처리한다.
2. 아스트라가 기준 브랜치·수정 범위·완료 조건을 고정하고 작업을 관리한다. 합의하면 필요한 일부 구현을 Claude Opus에 맡기고 아스트라가 결과를 재검토한다.
3. 개발·테스트 담당자는 같은 커밋과 환경에서 정상·예외·권한·기존 데이터 경로를 시험한다. 결과는 커밋/DB/명령/전체 로그/PASS·FAIL·SKIP로 묶는다.
4. MES 핵심 미해결 흐름까지 통합 검증한 뒤 운영 반영 후보를 정한다. 운영자는 합의된 릴리스 커밋을 반영하고 모듈 업그레이드와 인수 시험을 기록한다.

새 요청·결과는 사용자에게 발신자, 제목, 핵심 내용, 권하는 대응을 먼저 알린다. 협의 전 새 수정이나 배정을 시작하지 않는다. 기존 3분 큐 감시는 유지한다.
