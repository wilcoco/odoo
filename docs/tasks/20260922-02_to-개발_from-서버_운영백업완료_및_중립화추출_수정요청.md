## 1. 현재 판정과 개발 측 다음 조치

운영 `odoo18`의 원본 복구용 백업은 완료했다. 개발 전달용 중립화 덤프 추출, PR #10 머지, 실제 복제본 복원·업그레이드 리허설은 아직 완료하지 않았다.

개발 측은 §3의 중립화 추출 문제를 정본에서 수정하고, 수정 커밋·미러 대응 커밋/PR·검증 결과를 회신해 주기 바란다. 이 문서는 기존 7건 전체가 서버 측 재검토를 통과했다는 뜻이 아니다. 수정본 재검토 후 머지·최종 SHA 확정 단계로 진행한다.

이번 게시 범위는 결과 보고와 코드 수정 요청이다. 운영 배포·DB 변경·재기동·자격증명 교체·실물 설비 조작에 대한 추가 실행 승인을 부여하지 않는다. 별도 안내 메시지는 사용자가 보낸다.

중지 시작부터 nginx 경유 웹 복구 확인까지의 로그 간격은 약 16초이다. DB 덤프·압축·이미지 저장이 끝날 때까지 Odoo를 중지한 방식이 아니다.

백업 방식은 Odoo 정지 중 PostgreSQL 스냅샷을 내보내고, 첨부파일 목록도 같은 스냅샷으로 읽어 파일스토어를 복사한 뒤 Odoo를 복구하는 방식이다. 이후 `pg_dump --snapshot`이 동일 스냅샷으로 DB를 덤프할 때까지 내보낸 세션을 유지했다. PostgreSQL·nginx·MQTT·go_relay와 다른 DB 클라이언트는 이 실행에서 중지하지 않았다. 완료 직후 go_relay는 `Up 28 minutes`, nginx·PostgreSQL·MQTT도 기존 uptime을 유지했다.

포함: `odoo18.dump`, 해당 DB 파일스토어, 확인된 설정·애드온 경로 9개, 컨테이너·이미지·버전·DB 메타데이터, PostgreSQL globals, 실제 사용한 Odoo/PostgreSQL 기본 이미지 및 컨테이너 변경 목록. **원본 개인정보·자격증명이 포함된 비공개 복구 자료**이므로 전체 폴더를 개발 전달용으로 취급하지 않는다. 기본 이미지 저장은 컨테이너 쓰기 계층 전체를 포함하는 호스트 이미지 백업이 아니며, 실제 복구 시 변경 목록 확인이 필요하다.

별도 DB인 `t_silo` 및 FDW 원격 원천 데이터, 설비 상태, 호스트 전체는 이 백업에 포함하지 않았다. 기존 `localhost:8069` 테스트베드는 보존하고, 복제본 접속은 계획한 별도 8169 사용 여부를 포함해 격리·터널 조건을 확인한 뒤 확정한다.

### 앞선 백업 실패·502의 원인과 이번 변경

- 09:20의 첫 시도는 Odoo 정지 후 남은 DB 연결을 모두 오류로 취급해 덤프·파일스토어 복사 전에 종료했다. 해당 폴더에는 `INCOMPLETE` 표식과 초기 메타데이터만 남았고 DB 덤프·파일스토어가 없어 완성 백업이 아니다. 삭제하지 않고 보존했다.
- 당시 외부 DB 클라이언트 `10.10.21.21`은 사용자 설명상 운영 서버이며 연결을 유지해야 한다. `idle`만으로 쓰기 주체라고 판정하거나 연결을 강제 종료하지 않았다. 이번 실행 순간에는 외부 연결 0개였지만 수정본은 외부 연결이 있어도 보존하며, 사전 읽기 전용 검증에서는 해당 연결이 있는 상태도 통과했다.
- 첫 스크립트가 Odoo와 go_relay를 정지·재시작하는 과정에서 컨테이너 IP가 바뀌었고 nginx가 이전 Odoo IP를 계속 참조했다. nginx 오류 로그와 컨테이너 IP 대조로 확인했으며 reload 후 복구했다.
- v3는 Odoo만 정지하고, 재시작 뒤 `nginx -t` → reload → 실제 프록시 HTTP 확인을 수행한다. 파일 복사·덤프·스냅샷 실패 및 연결 종료 시 복구 처리도 합성 테스트로 검증했다. 이 합성 검증과 이번 실제 백업 성공을 실제 복원 리허설 성공으로 확대 해석하지 않는다.

### 수정본 회신에 필요한 검증 근거

1. 정본 수정 커밋·작업 문서, 미러 대응 커밋/PR, 변경 파일·새 head를 기재한다. handoff에는 실행 스크립트 원본을 추가하지 않는다.
2. 합성 테스트: 중립화 SQL 입력 전달, 스키마 복원 오류, 데이터 복원 오류, 기존 임시 DB 충돌, 개인정보 잔존을 각각 검증하고 실패 시 전달물 완료가 되지 않음을 확인한다.
3. 격리된 PostgreSQL 17 테스트: 식별정보가 있는 합성 원본 → 마스터 복원 → 중립화 → 재덤프 → 별도 검증 DB 재복원 → 마스터 건수·관계 및 잔존 정보 검사까지 수행한다. 사용 커밋·DB/환경·명령·검사 결과를 회신한다.
4. 가짜 Docker 하네스·셸 문법 검사와 실제 PostgreSQL 테스트를 구분한다. 서버 담당은 수정본 검토 후 운영 호스트 안에서 추출·검증하고 승인된 파일만 전달한다.

## 4. 전달물과 PR·리허설 순서

큐 20260921-02의 원본 전달 후 개발 측 중립화 방식은 사용하지 않는다. 최신 회신대로 **서버 안에서 중립화·검증을 완료한 후** 아래 네 파일만 전달 대상으로 한다.

```text
uat_master_neutralized.dump
schema_master_tables.sql
neutralize_check.txt
SHA256SUMS
```

전달 대상은 홍정수이다. 사용자가 공유 드라이브가 아니라고 정정했으므로 전달 수단·접근 범위를 별도로 확정한다. 현재는 중립화 덤프 생성·전달을 완료하지 않았다. Git·큐에는 상태·검사 요약·민감하지 않은 전달 식별 정보만 기록한다.

게시 준비 시 원격 재조회 결과:

- PR #10 head: `4a4be9a952d9481b09fcdfa68ef6c51b3644ee46`
- 미러 main: `ce759f5da91ac215e2fd8531e8f6a32376264825`
- 확인한 handoff 기준: `9abf1f6482a1ff2d724730f59937b0e54005677e`

중립화 및 기존 차단 사항 수정본 재검토 → PR 머지 → 실제 main에 반영된 최종 40자리 SHA 회신 → 해당 SHA로 격리 검사·복원·업그레이드·화면·복구 리허설 → 결과 보고 후 운영 일정 별도 결정 순서로 진행한다. 현재 PR head나 GitHub의 시험용 merge ref를 최종 머지 SHA로 통보하지 않는다.

`flushing/20260918`의 로컬 추가 커밋 3개는 사용자 지시에 따라 로컬에만 유지하며 push하지 않는다. 이번 문서 게시에도 포함하지 않는다. 해당 브랜치를 미러 main에 직접 병합하지 않는다.

## 5. 별도 현장 회신으로 남은 항목

다음은 이번 백업으로 확인된 사실이 아니며, 확인 전까지 미확인 상태를 유지한다.

- 백업 후 실제 사출/API 입력 정상 재개 여부 및 시사출 시각·MO·시리얼·양품/불량·사일로 변화·오류 화면.
- 사용자 설명의 사출 완료 경로는 취출로봇 → PLC 업체 푸시 → 미들웨어 → `/api/plc/complete`이다. 실제 발신 장치/IP·프로그램 버전·재전송 규칙은 추가 확인이 필요하다. go_relay는 이종검사용 Go MQTT 중계이며 그것만 중지해 사출 입력을 차단할 수 있다고 가정하지 않는다.
- `t_silo`는 같은 PostgreSQL 17 서버의 별도 DB이고 Odoo가 FDW로 조회한다는 사용자 설명을 기준으로 한다. 실제 작성 프로그램·센서 단위·갱신 주기는 미확인이다.
- go_relay 실제 빌드 커밋·설정, 조립 통신 서버 PC·실행 프로그램, BR 수신·재처리 경로의 미확인 사항. 설정·로그 회신 시 비밀값을 제거한다.
- 업무 확인: `TEST-INJ-TPO`·`TEST-SILO` 용도, 미분류 품목 210건의 의미, 표준 예비 BOM 29건 폐기 가능 여부. 업무 담당 확인 없이 임의 삭제·변경하지 않는다.
- 노출 자격증명 교체는 미실행이다. 사용처 확인 → 저장소 밖 설정 → 새 값 적용·검증 → 기존 값 폐기 순서로 별도 처리한다. 코드에서 값을 지우는 것만으로 기존 값이 폐기되지는 않는다.

개발 측 회신은 본 파일에 수정 커밋·검증 결과·남은 확인 사항을 붙이고 상태를 갱신해 주기 바란다.
