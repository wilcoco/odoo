### 5.1 [P1] pg_restore의 마지막 '-' 인자를 제거

아래 줄 번호는 검토한 a60c19c 및 파일 트리가 동일한 머지 커밋 ce759f5 기준이다.

영향 위치:

- scripts/release/rehearse.sh:27
- scripts/release/release_core.sh:96
- scripts/release/release_rollback.sh:21
- 최종 절차서의 백업 무결성 검사 및 롤백 명령

실제 postgresdb에서 DB에 쓰지 않는 --list 검사를 빈 stdin으로 실행한 결과:

```text
pg_restore: error: could not open input file "-": No such file or directory
pg_restore_list_dash_exit=1
```

반면 마지막 '-'를 생략하면 표준입력을 읽고 “input file is too short (read 0, expected 5)”를 반환했다. 빈 입력이므로 두 번째 실패는 정상이며, 표준입력 처리 차이를 확인하기 위한 검사다.

현재 스크립트의 '-'는 파일명으로 처리된다. 복제본 첫 복원은 실패하고, 운영 apply는 Odoo를 중지한 뒤 백업 목록 검사에서 멈추며, rollback도 같은 문제로 복원하지 못한다. docker exec -i와 호스트 리다이렉션을 유지하되 pg_restore의 파일 인자를 생략해야 한다. 실제 DB 복원은 수행하지 않았다. 이전 절차서에도 있던 동일 표기를 함께 수정해야 한다.

### 5.2 [P1] 복제본 config/코드를 Odoo UID가 읽을 수 있게 준비

영향 위치: rehearse.sh:18,31~35 및 release_core.sh:49~53.

root로 실행하면서 umask 077을 설정한 후 config를 생성하므로 신규 odoo.conf는 root 소유 600이 된다. clone 파일·하위 디렉터리도 제한된 권한이 될 수 있다. 반면 실제 이미지 사용자는 100:101이고 docker run에 사용자 변경이 없다. 현재 스크립트에는 소유자/그룹 정렬이 없어 config와 addons를 읽지 못할 수 있다.

복제본 전용 경로에 한해 Odoo UID/GID와 읽기·탐색 권한을 명시적으로 맞추고, 컨테이너 사용자로 config/manifest/filestore 접근을 사전 검증해야 한다. 비밀값이 있는 config를 무조건 전세계 읽기 가능으로 만드는 방식은 피한다. 운영 폴더의 소유권은 변경하지 않는다.
