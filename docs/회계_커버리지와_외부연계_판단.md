# 회계 커버리지 진단 — 어디까지 되고, 한국 실정상 무엇을 붙여야 하나

작성: 2026-08-26 · 근거: 설치 모듈 실사 + 소스 확인(l10n_kr / l10n_kr_reports / account_kr_* / hr_payroll_kr)

## 0. 한 줄 결론

**장부(분개·원장·재무제표)와 사내 통제(정산·마감·검증)는 이 구성으로 충분히 돌아갑니다.
반면 "국가기관·금융기관과 데이터를 주고받는 구간"은 Odoo에 없습니다** — 세금계산서 발행,
은행 거래내역, 4대보험·원천세 신고가 그것이며, 현재는 전부 **사람이 홈택스·은행에서
받아다 넣는 수작업**입니다. 붙일지 말지는 "월 몇 건이냐"로 결정하면 됩니다.

## 2. 비어 있는 구간 — 한국 실정상 외부 서비스가 필요한 곳

### ⓐ 전자세금계산서 발행·수취 (가장 큰 구멍)

- **현재**: Odoo는 세금계산서를 **발행하지 못합니다.** 홈택스(또는 ASP)에서 발행하고,
  승인번호를 Odoo에 적어 넣는 구조입니다. 수취분도 홈택스에서 내려받아 CSV로 올립니다.
- **왜 Odoo에 없나**: `account_edi_ubl_cii`는 유럽 표준(UBL/CII) 전자문서이고 국세청
  전자세금계산서 규격과 무관합니다. Odoo 한국 로컬라이제이션에는 발행 연동이 없습니다.
- **붙인다면**: 국세청 ASP(팝빌·바로빌·더존 등)의 발행 API. 매출 전표 게시 →
  API 발행 → 승인번호 자동 회신 저장, 매입은 수취분 자동 수집.
- **판단 기준**: 월 발행 **30건 이하면 수작업 유지**가 합리적입니다(현 흐름으로 충분).
  100건을 넘거나 마감이 상시 지연되면 연동이 회수됩니다.

### ⓑ 은행 거래내역 (펌뱅킹/스크래핑)

- **현재**: 파일(CSV/OFX/CAMT) 업로드만 됩니다. 자동 수집은 `account_online_synchronization`이
  설치돼 있으나 이는 **해외 은행 aggregator(Ponto/Salt Edge 등)** 대상이라 **국내 은행은 사실상 미지원**입니다.
- **붙인다면**: 금융결제원 펌뱅킹 또는 스크래핑 서비스(뱅크다·쿠콘 등) → 거래내역 자동 반입 + 이체 실행.
- **판단 기준**: 계좌 2~3개면 은행 사이트에서 월 1~2회 내려받아 업로드가 낫습니다.
  **자동이체·대량 지급이 있으면 펌뱅킹**을 검토하세요.

### ⓒ 4대보험 · 원천세 신고

- **현재**: `hr_payroll_kr`이 **고지 금액 반영·원천세 집계(A01)**까지 만들고, EDI 고지 파일을
  업로드해 읽는 골격이 있습니다. 그러나 **신고서 전송은 없습니다** — 4대보험 EDI 사이트와
  홈택스에서 사람이 신고합니다.
- **붙인다면**: 4대보험 EDI 연계, 홈택스 원천세 신고 API. 다만 국내 관행상
  **세무대리인(기장 사무소)이 신고를 대행**하는 경우가 많아, 이 구간은 연동보다
  **집계표를 정확히 뽑아 세무사에게 넘기는 것**이 현실적입니다.

### ⓓ 부가세 신고서 서식

- **현재**: 세목이 신고서 라인 코드(GT…)에 매핑돼 있어 **집계는 정확**하지만,
  국세청 서식 그대로의 신고서 출력물은 없습니다.
- **붙인다면**: 신고서 서식 리포트 자체 개발 또는 세무대리인 제출용 집계표로 대체.
  → **집계표 대체를 권장**합니다(개발 대비 효익이 낮음).

### ⓔ 기타 한국 특수 항목 (필요 시점에 검토)

| 항목 | 상태 | 비고 |
|---|---|---|
| 전자어음·외상매출채권(팩토링) | 없음 | 실제 사용 여부 확인 후 결정 |
| 법인카드 매입 자동 수집 | 없음 | 여신협회/카드사 연동 또는 카드사 CSV 업로드 |
| 현금영수증 발행 | 없음 | B2B 위주면 불필요 |
| 지방세·법인세 신고 | 없음 | 세무대리인 영역 |
| K-IFRS 별도 공시 | 미대상 | 외부감사 대상 여부에 따름 |

## 3. 지금 당장 확인해야 할 것 (설정 리스크)

1. **운영 서버의 계정과목표가 한국(l10n_kr)인지 확인** — 로컬 개발 DB는 `generic_coa`(미국
   샘플 회사)로 되어 있습니다. 개발용이라 문제는 없지만, **운영 DB가 generic_coa이면
   부가세 세목·재무제표가 한국식이 아닙니다.** 계정과목표는 거래 발생 후 교체가 매우 어려우니
   **양산 개시 전에 반드시 확인**하세요. (확인: 설정 › 회계 › 재정 현지화)
2. **재고 평가 방식(수동/자동)** — 자동이면 입고 시 분개가 생기고 수동이면 정산 시점에만
   생깁니다. 현재 전제는 "수동"입니다. 원가 관리 정책과 맞는지 회계 담당 확인 필요.
3. **불필요 모듈 정리** — `l10n_us*`, `account_avatax*`(미국 세금 서비스),
   `account_qr_code_sepa`(유럽), `l10n_us_hr_payroll*`이 설치돼 있습니다. 동작에 해는
   없지만 메뉴·필드가 섞이고 오설정 위험이 있어 운영 DB에서는 제거를 권합니다.

## 4. 권고 (우선순위)

| 순위 | 조치 | 이유 |
|---|---|---|
| 1 | **운영 DB 계정과목표 = 한국인지 확인** | 나중에 못 바꿈. 리스크 최대 |
| 2 | 세금계산서는 **당분간 수작업 유지** (홈택스 발행 → 승인번호 기입/CSV 반입) | 이미 대량 반입·중복차단·백필 매칭이 갖춰져 있음 |
| 3 | 은행은 **파일 업로드로 시작** | 계좌 수가 적으면 연동 비용이 회수되지 않음 |
| 4 | 4대보험·원천세는 **집계표 → 세무대리인** | 국내 관행상 가장 저렴하고 안전 |
| 5 | 발행 건수가 월 100건을 넘거나 마감이 상시 지연되면 **ASP 발행 API 연동** 재검토 | 그때가 손익분기 |
