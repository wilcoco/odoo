## Phase R — 동시성 (병렬 트랜잭션)
| 테스트 | 결과 |
|---|---|
| R1 동시 20 부적합(NC) 생성 | ✅ 시퀀스 20개 전부 고유(중복 없음) |
| R2 동시 10 SILO 소비 | ✅ 오버셀·음수 없음(REPEATABLE READ가 충돌 txn을 SerializationFailure로 거부). ※ 처리량 저하 → 재시도 로직 권장(운영노트) |
| **R3 동시 5 톤정산 매입계산서** | ⚠️→✅ **결함→수정**: 멱등가드(`if move_ids`)가 RR 스냅샷이라 동시 5→**5장 발행**되던 race |
| R4 동시 2 소요통보 cron | ✅ 통보 1건(중복 없음) |

**수정(R3)**: `move_ids` 가드만으론 REPEATABLE READ에서 각 txn이 '없음' 스냅샷을 봐 중복 발행. → `bills_created` 플래그를 **정산 행에 UPDATE** 하여 동시 두번째 커밋을 `serialization_failure`로 롤백 → 1건만 발행. 순차 재클릭도 플래그로 차단.
**재검증**: 동시 5 → 1건(1성공+4 SerializationFailure 자동롤백).

> **벤더 정산위저드(gh_vendor_settlement) 동시성 = 검증완료 안전**: 동시 3 실행 → 1 made + 2 SerializationFailure(자동 롤백). accrual `state="billed"` UPDATE가 RR 직렬화를 이미 제공 → 중복발행 없음. **R3 수정 원칙(행 UPDATE 직렬화)이 이 모듈에선 이미 적용돼 있음을 역으로 확인.**

## 결론 (20명 동시 사용 대비)
- **문서·기록 번호(시퀀스)**: 동시 생성해도 중복 없음 ✅
- **재고·통보 동시**: DB 격리(RR)로 무결성 보호(오버셀·중복 없음), 단 경합 시 재시도 필요(운영 UX) ✅
- **중복 발행 방지**: 멱등가드는 순차엔 되나 **동시엔 행-업데이트 직렬화가 추가로 필요** → 톤정산 수정 완료(R3). 같은 원리를 신규 "생성/발행" 액션 설계 시 기본 적용 권장.
- **권한**: 재무 마스터(계약단가·정산) 삭제를 관리자로 제한(P1·P2 수정). 심사/결재는 지정자만.
- **승인**: 결재선·권한·리셋 정상.

## 부속(설계 원칙 — 향후 개발 반영)
동시 사용 환경에서 "한 번만 생성/발행" 보장이 필요한 액션은 (a) 스냅샷 가드(move_ids/flag 읽기)만으로 부족 → (b) **대상 행 자체를 UPDATE(플래그)해 RR 직렬화** 또는 SELECT FOR UPDATE + 행변경 병행. 대량동시 진입 액션엔 SerializationFailure 재시도(UX) 고려.
