# 전자세금계산서 발행 · 은행 연동 — 자체 개발 검토

작성: 2026-08-27 · 배경: 운영 DB 계정과목표 한국 확인됨 → 남은 공백은 "외부 기관 연계" 구간

> 결론 먼저: **둘 다 자체 개발 가능하고, 둘 다 "중계 서비스 API를 붙이는 방식"을 권합니다.**
> 국세청·은행과 **직접** 연결하는 방식은 기술 문제가 아니라 **자격·계약·법적 책임** 문제라
> 우리 규모에서는 비용이 회수되지 않습니다.

---

## 1. 전자세금계산서 발행

### 1-1. 선택지 3가지

| 방식 | 무엇인가 | 우리가 만들 것 | 진입 요건 | 현실성 |
|---|---|---|---|---|
| **A. 홈택스 수동** (현행) | e-세로에서 사람이 발행 → 승인번호를 Odoo에 기입 | 없음 (이미 구현됨) | 없음 | 건수 적으면 최적 |
| **B. ASP API 연동** ★권장 | 팝빌·바로빌·더존 등 발급대행사 REST API 호출 | **Odoo 커넥터 모듈** | 계약 + 건당 과금 | 개발 2~4주, 리스크 낮음 |
| **C. 국세청 직접 연계** | 자체 발급 시스템을 국세청에 직접 전송 | 커넥터 + XML 규격 + 전자서명 + 전송·재전송·오류처리 | **전자세금계산서용 공동인증서**, 국세청 표준 XML 규격 준수, 발급 다음날까지 전송 의무, 장애 시 가산세 책임 | 대기업 방식. 우리 규모엔 과함 |

**C를 권하지 않는 이유**는 개발 난이도가 아니라 **책임 구조**입니다. 전송 지연·누락이
곧 가산세이고, 국세청 규격이 바뀌면 우리가 따라가야 하며, 인증서 갱신·장애 대응을
상시 떠안게 됩니다. B는 그 책임을 대행사가 집니다(SLA·전송보장).

### 1-2. B안으로 갈 때 우리가 개발할 것

이미 **필드는 다 있습니다** — 승인번호(중복 차단), 과세구분, 증빙종류, 수정분 원본번호 연결.
붙일 것은 "전표 ↔ 대행사" 사이의 배관뿐입니다.

| 기능 | 내용 |
|---|---|
| 발행 요청 | 매출 전표 [게시] 후 [세금계산서 발행] 버튼 → 대행사 API 호출 (공급자/공급받는자/품목/세액/비고) |
| 승인번호 회신 | 응답의 국세청 승인번호를 `kr_approval_number`에 저장 → 이미 있는 중복 차단이 그대로 작동 |
| 상태 동기화 | 발행중/발행완료/국세청 전송완료/실패 상태 필드 + 재시도 (크론) |
| 수정발행 | 환불·수정 전표에서 수정사유 코드 + 원본 승인번호(`kr_origin_number` 기존 필드) 전송 |
| 역발행·매입 수집 | 매입분 조회 API로 수취분 자동 적재 → 현재 CSV 업로드를 대체 |
| 실패 처리 | 사업자번호 오류·휴폐업·한도 초과 등 오류코드를 채터에 한글로 안내 |

**공수 추정**: 발행·승인번호·상태 동기화까지 **2주**, 수정발행·매입 자동수집·오류 처리 포함 **3~4주**.
(대행사 API는 REST/JSON이라 난이도보다 **케이스 정리**가 일의 대부분입니다.)

**운영 비용**: 건당 과금(수십~백 원대) + 월 기본료 수준. 정확한 금액은 견적 필요 —
**월 발행 건수를 먼저 세어야** B와 A의 손익분기가 나옵니다.

### 1-3. 판단 기준

- 월 발행 **30건 이하** → A 유지 (개발·과금 대비 효익 없음)
- 월 **100건 이상**이거나 마감이 상시 지연 → **B 착수**
- 그 사이 → 발행 담당자의 실제 소요 시간(건당 몇 분 × 건수)으로 계산

## 2. 은행 연동

### 2-1. 선택지

| 방식 | 무엇인가 | 요건 | 우리 적합도 |
|---|---|---|---|
| **A. 파일 업로드** (현행) | 은행 사이트에서 거래내역 내려받아 Odoo에 업로드 | 없음 (CSV/OFX/CAMT 이미 지원) | 계좌 수 적으면 충분 |
| **B. 계좌조회 API(스크래핑/집계 서비스)** ★권장 | 쿠콘·CODEF 류 서비스가 은행 계좌를 대신 조회 → 우리는 REST로 수신 | 서비스 계약, 계좌 인증정보 위임 | **조회 자동화에 최적** |
| **C. 펌뱅킹** | 은행과 직접 계약, 전용 규격으로 조회+**이체 실행** | 은행별 계약·전용 규격·보안 심사 | 대량 이체가 있을 때만 |
| **D. 오픈뱅킹(금융결제원)** | 표준 API | **핀테크 사업자 등록 필요** — 자사 계좌 관리 목적엔 부적합 | 해당 없음 |

> Odoo에 설치된 `account_online_synchronization`은 **해외 은행 aggregator 전용**이라
> 국내 은행에는 쓸 수 없습니다. 국내는 B/C를 직접 붙여야 합니다.

### 2-2. B안으로 갈 때 우리가 개발할 것

| 기능 | 내용 |
|---|---|
| 계좌 등록 | 회사 계좌별 서비스 연결 정보 (**자격증명은 DB 파라미터 — 코드·git 금지**, 기존 오라클 연동과 동일 원칙) |
| 일 1~수회 수집 | 크론이 거래내역 조회 → `account.bank.statement.line` 생성, **거래 고유키로 멱등** 처리 |
| 자동 매칭 | 입금은 거래처명·금액으로 미수금, 출금은 미지급금 후보 제시 (Odoo 표준 조정 화면 활용) |
| 예외 처리 | 인증 만료·한도·서비스 장애 시 담당자 알림 + 수동 업로드 폴백 유지 |

**공수 추정**: 수집·멱등·조정 연결까지 **2~3주**. 이체 실행(C)은 **범위에서 제외** 권장 —
자금 이체는 오조작 손실이 즉시 발생하고 보안 심사 부담이 커서, 초기엔 **조회만 자동화**하고
이체는 사람이 은행에서 하는 편이 안전합니다.

### 2-3. 판단 기준

- 계좌 2~3개, 월 거래 수십 건 → **A 유지**
- 계좌가 많거나 **일일 자금 현황을 매일 봐야 함** → **B 착수** (이미 만든 자금 현황·수금/지급
  예정표가 실시간으로 살아납니다)
- 대량 자동이체(급여·협력사 대금 일괄) → C를 별도 과제로

## 3. 권고 순서

| 순위 | 과제 | 근거 |
|---|---|---|
| 1 | **월 발행 건수·계좌 수 실측** (1일) | 이 숫자 없이는 B/A 판단이 불가. 담당자에게 물으면 끝 |
| 2 | **은행 조회 자동화(B)** 먼저 | 세금계산서보다 **법적 책임이 없고**, 이미 만든 자금 리포트가 즉시 살아남 |
| 3 | **세금계산서 ASP 연동(B)** | 대행사 견적 2곳 비교 후 착수. 필드·중복차단은 이미 있어 배관만 붙이면 됨 |
| 4 | 이체 실행·국세청 직접연계 | 당분간 **하지 않는다**로 명시 (책임·보안 부담이 효익을 초과) |

### 착수 전 확인해야 할 것
- 대행사 선정: **매입 수취분 조회 API 제공 여부**를 반드시 확인 (없으면 CSV 수작업이 남음)
- 인증 방식: 사업자 인증서 보관 주체가 대행사인지 우리인지
- 테스트 환경(샌드박스) 제공 여부 — 실발행으로 테스트하면 취소·수정발행 이력이 국세청에 남음
