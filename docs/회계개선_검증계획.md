# 회계 개선(오두 회계 사용 리포트) 검증 계획

> 목적: 「오두 회계 사용 리포트」의 개선요청 33개 항목(§2–§34)을 다른 세션이 통합 구현한 결과를,
> **그 세션의 작업을 방해하지 않고** 별도 환경에서 "빠짐없이(커버리지) + 오류없이(정합성)" 점검한다.
> 검증 주체는 구현 세션과 다른 세션/사람이어야 한다 (자기 채점 금지).

---

## 0. 비간섭 원칙 (검증 환경 규칙)

1. **구현 세션의 작업트리·브랜치·DB를 직접 만지지 않는다.**
   - 코드 확인은 `git worktree add /tmp/wt-acct-verify <구현브랜치>` 로 별도 워크트리에서. 구현 세션이 쓰는 체크아웃 디렉토리는 읽기도 자제(파일락·pyc 오염 방지).
   - 구현 세션이 쓰는 DB(이름 확인 후)는 **접속 자체를 하지 않는다**. 검증은 전용 복제 DB(`acct_verify_*`)를 새로 만들어 사용.
2. 운영/기준 DB(cams, cams_demo)는 `pg_dump` 읽기만. 복제본에서만 설치·시나리오 실행.
3. 검증 중 발견한 결함은 **고치지 말고 기록만** 한다(수정은 구현 세션 몫 — 이중 수정 충돌 방지).
4. 완료 판정 전 반드시 **원격 존재 확인**: `git ls-remote --heads` 로 구현 브랜치가 원격에 있고, 핵심 심볼이 원격 ref 에서 `git grep` 되는지. (로컬 커밋·마운트 동작 ≠ 인계 — G1-G5 push 누락 전례)

## 1. 1단계 — 커버리지 매트릭스 (빠짐없이 했는가)

구현 브랜치에서 **항목→구현물(모델/필드/뷰/가드/테스트) 추적표**를 먼저 만든다.
방법: 각 항목의 열쇠 심볼을 워크트리에서 grep → 구현물 기록. **구현물이 하나도 안 잡히는 항목 = 누락 후보**로 명시(조용한 축소 금지). "코드가 아니라 DB 설정(자동화 규칙·Live View)으로 처리"된 항목은 별도 표기(§7 참조 — 코드화 여부가 쟁점).

## 2. 2단계 — 항목 간 관계(통합) 검증 (따로 만들어 어긋나지 않았는가)

리포트 항목들은 6개 축으로 얽혀 있다. **같은 개념이 두 곳에서 다르게 정의되면 실패**로 본다.

### 축 A. 거래처 마스터 (§2·§3·§16·§22·§28)
- 사업자등록번호가 **단일 필드**인가(§3 중복검사, §16 세금계산서 대사, §22 은행매칭, §28 체크리스트가 모두 같은 필드를 참조하는지 grep 으로 확인).
- §2의 거래처 유형 구분값과 §3의 중복 안내, §28의 "사업자번호 없는 거래처" 점검이 같은 분류 체계를 쓰는가.

### 축 B. 세금계산서 (§15→§16→§17→§18→§29)
- 승인번호·발행번호·원본번호가 **한 모델의 같은 필드**로 관통하는가(업로드에서 넣은 값이 중복검사·수정분 연결·합계표·매입매출장에서 그대로 조회).
- 시나리오: 과세 1건 업로드 → §16 재업로드 차단 → §17 마이너스(원본 연결) 업로드 → §18 집계에 수정분 별도 반영 → §29 매입매출장에 원본+수정 2행, 합계 상쇄 확인.

### 축 C. 금액 정합 (§4·§5·§14·§27·§28)
- 청구서 화면의 "남은 금액"(§4·§14)과 §27 대사 화면의 잔액, §28 체크리스트의 불일치 검출이 **같은 계산식/필드**(amount_residual 등)를 쓰는지. 화면마다 자체 계산이면 결함.
- 시나리오: 부분결제 1건 → 세 화면의 잔액이 동일 금액인지.

### 축 D. 결제 라이프사이클 (§12·§13·§21·§22·§30)
- §12(사전 차단)와 §13(취소 정합)과 §28(사후 감지)이 **같은 '고아' 정의**를 쓰는가.
- 시나리오: 미결계정 없는 저널로 결제 시도 → 차단(§12) / 결제 후 취소 → 청구서·결제 상태 동시 정리(§13) → §21 자금현황과 §30 예정표에서 취소 반영 확인.

### 축 E. 승인·권한·이력 (§6·§7·§8·§33·§34)
- **가드 일치**: "승인 전 지급 불가"(§7)가 UI 버튼 숨김만이 아니라 서버 메서드에서도 막히는가(RPC 직접 호출로 시도). §8 권한 매트릭스와 §33 제한행위 목록이 같은 그룹을 참조하는가.
- §34 잠금 해제가 §33 이력에 남는가(해제→수정→재잠금 시나리오).

### 축 F. 업로드 공통 패턴 (§15·§22·§23)
- 미리보기/오류행 분리/중복검사/결과요약이 **공통 위저드·믹스인**인지, 화면마다 복붙인지(복붙이면 중복 기준 불일치 위험 — 각 화면에서 같은 파일 2회 업로드로 동작 비교).

### 축 G. 자동화 이중실행 (§5·§12 ↔ §32) ⚠️ 최우선
- 리포트에 "현재는 자동화 규칙으로 조치했다"고 명시된 것들(§5 총계 자동계산, §12 고아결제 감지, §15 Live View 수정)이 **DB 안의 임시 자동화(base_automation)로 남아 있는 상태에서 모듈 코드가 또 들어오면 이중 실행**된다.
- 확인: 검증 DB에서 `base.automation`/서버액션 목록 조회 → 신규 모듈 기능과 겹치는 규칙 존재 여부 → 겹치면 "임시규칙 비활성화 마이그레이션"이 구현에 포함돼 있는지. **없으면 결함(총계 2회 계산, 알림 2회 발송 등)**.

## 3. 3단계 — 파괴 시나리오 (오류없이 되는가; 해피패스 금지)

복제 DB에서 아래를 실제로 실행한다. 각각 기대결과 명시.

1. **중복 2연타**: 같은 세금계산서 파일 연속 2회 업로드 → 2회차 전량 오류목록, 전표 0건 생성. 같은 사업자번호 거래처 2회 생성 → 안내 후 기존 사용 유도.
2. **동시성**: 같은 청구서에 결제 등록을 두 세션에서 동시에(odoo shell 2개, 커밋 경쟁) → 이중 결제/이중 전표 없어야 함. (멱등 가드만으론 RR 격리에서 뚫린 전례 — 행 UPDATE 직렬화 여부 확인)
3. **재실행+입력보존**: §23 업로드 → 일부 행 수기 보정 → 오류행 재업로드 → **수기 보정이 날아가지 않는지**.
4. **엣지 금액**: 면세(세액 0)·영세(0%)·마이너스·부분환불·원화인데 통화 비어있는 전표(§11 재현) 각 1건 → 총계·집계·원장 정상, §11 메시지가 한글 안내로 나오는지.
5. **권한 우회 시도**: 일반직원 계정으로 확정전표 삭제·결제취소·잠금해제를 **RPC 직접 호출** → 서버단 거부(화면 숨김만으론 실패).
6. **마감 잠금**: 잠금 → 과거일자 전표 입력 시도(차단) → 관리자 해제 → 입력 → 재잠금 → 해제/수정 이력이 §33 로그에 남는지.
7. **§28 체크리스트 실효성**: 위 시나리오들이 만든 오염(0원 청구서·고아결제·원본 없는 마이너스 등)을 일부러 남긴 뒤 체크리스트 화면이 **전부 잡아내는지** (검출 누락 = 실패).

## 4. 4단계 — 시스템 수준 검증 (기존 인프라 재사용)

1. **신선 설치**: `ci/run_tests.sh <신규모듈목록>` — 빈 DB 설치 + 신규 테스트 0 failed (테스트가 아예 없으면 그것대로 기록 — 승격 요구).
2. **업그레이드 회귀**: `ci/upgrade_regression.sh cams <신규모듈목록>` — 운영 복제본에 -u all + 신규 모듈 -i 설치 후:
   - 불변량(전표 건수·금액합) 불변 — **회계 개선이 기존 회계 데이터를 건드리면 즉시 적발됨. 이번 검증에서 가장 중요한 게이트.**
   - 새 오류 0 (기준선 대비).
3. **머지 무결성**: `ci/critical_symbols.txt` 에 이번 구현의 핵심 심볼(품의서 모델명, 승인번호 필드, 고아결제 감지 메서드, 잠금해제 로그 등 5–10개) 추가 후 `ci/merge_integrity_check.sh` — 이후 머지에서 유실 감시.
4. **Odoo 18 컨벤션**: 워크트리에서 `grep -r "<tree" views/`, `grep -r "attrs="` = 0건. `ir.model.access.csv` 에 신규 모델 전부 등재(빠지면 일반 사용자 화면 크래시).
5. **데모/실데이터 분리**: 신규 모듈 demo 데이터가 운영 DB 설치 시 흘러들지 않는지(-i 후 demo 레코드 검색 0건).
6. **원격 존재**: `git ls-remote` + 원격 ref 심볼 grep + (구현이 마운트 디렉토리에서 이뤄졌다면) 마운트 ↔ 원격 브랜치 diff 0.
