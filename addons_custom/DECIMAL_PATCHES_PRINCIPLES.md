# plus_patch 2종이 지향하는 것

> `account_kr_plus_patch` · `mrp_plus_patch` 의 설계 원칙.
> "무엇을 하는가"는 `DECIMAL_PATCHES_GUIDE.md`, 이 문서는 **"왜 그렇게 만들었는가"** 입니다.

## 한 문장

**설정이 닿는 곳은 설정에 맡기고, 코드는 설정이 닿지 않는 곳에만 쓰되,
언제든 떼어낼 수 있게 만든다.**

---

## 지향점 7가지

각 항목은 이번 작업에서 실제로 내린 결정이며, "지키지 않았다면" 은 그 결정을
포기했을 때 벌어졌을 일입니다.

### 1. 설정으로 되는 일에 코드를 쓰지 않는다

통화 반올림 계수(KRW=1)가 이미 `Monetary` 금액 **전부**를 0자리로 처리하고
있었습니다. 그 영역에는 코드를 **한 줄도** 쓰지 않았습니다. 코드는 설정이
물리적으로 닿을 수 없는 부류 — `digits` 미지정 Float 15개 — 에만 들어갑니다.

> 지키지 않았다면: 이미 정상 동작하는 영역을 코드가 이중으로 강제하게 되고,
> 회계팀이 통화 설정을 바꿔도 시스템이 말을 듣지 않습니다.

### 2. 하나의 손잡이가 두 도메인을 흔들지 않게 한다 — 이 작업의 핵심

2026-03-05 사고의 구조적 원인은 **금액과 수량이 한 손잡이를 공유**한 것이었습니다.
금액의 `.00` 을 없애려고 소수점 정확도를 내리자 수량 소수점이 함께 죽었습니다.

지금은 손잡이가 셋으로 분리됩니다.

| 손잡이 | 담당 |
|---|---|
| `KR Amount` | 금액 (합계·잔액·평가액) |
| `Product Price` | 단가 |
| `Product Unit of Measure` | 수량 |

> 지키지 않았다면: 다음에 금액 표시를 손댈 때 수량이 또 깨집니다.
> **같은 사고가 반복 가능한 상태로 남는 것**이 가장 큰 손실입니다.

### 3. 운영자의 설정을 덮지 않는다

모듈은 **기본값을 제안**할 뿐, 최종 결정권은 운영자에게 있습니다.

- 소수점 정확도 레코드는 설치 때 한 번만 심습니다 (업그레이드가 덮지 않음)
- 수량 자리수는 **2 미만일 때만** 올립니다 — 3자리로 써 온 DB는 건드리지 않음
- 다른 모듈이 이미 자리수를 지정한 필드는 손대지 않음

> 지키지 않았다면: 업그레이드할 때마다 회계팀이 맞춰 둔 설정이 되돌아갑니다.
> 그 순간부터 아무도 그 모듈을 신뢰하지 않습니다.

### 4. 영리함보다 예측 가능성 — 화이트리스트

`amount`, `price` 같은 이름 패턴으로 긁으면 코드는 짧아집니다. 그렇게 하지
않고 대상 15개를 손으로 적고 표로 문서화했습니다.

> 지키지 않았다면: 이자율·환율·비율처럼 이름이 금액을 닮은 Float가 휩쓸려
> 계산이 틀어집니다. 돈이 걸린 시스템에서 **"왜 이게 바뀌었지"** 는 치명적입니다.

### 5. 표시 문제는 표시 계층에서 끝낸다

저장 필드는 자리수를 바꾸면 DB 컬럼 타입까지 바뀝니다. 그런 필드는 **자동으로
건너뛰도록** 만들었습니다. 이 패치로 발생하는 스키마 변경·마이그레이션은 0건입니다.

> 지키지 않았다면: 화면의 `.00` 을 지우려다 컬럼 타입 변경과 저장값 반올림까지
> 끌어들이게 됩니다. 표시 개선의 대가로는 너무 비쌉니다.

### 6. 남의 모듈을 고치지 않는다 — 떼어낼 수 있게 만든다

`account_kr_guard` 는 담당자가 따로 있고 수정이 민감합니다. 그래서 본체를
건드리지 않고 **별도 모듈로 얹었습니다**. 언인스톨하면 흔적 없이 원복되고,
편입 여부는 소유자가 문서(`HANDOVER.md`)를 보고 결정합니다.

> 지키지 않았다면: 권한 밖의 수정이 되고, 문제가 생겼을 때 롤백하려면 그 모듈의
> 다른 기능까지 함께 되돌려야 합니다.

### 7. 의도를 주석이 아니라 테스트로 고정한다

"수량은 건드리지 않는다", "3자리를 2로 끌어내리지 않는다" — 이 두 약속은
주석이 아니라 **실행되는 테스트**입니다.

> 지키지 않았다면: 다음 담당자가 선의로 수량 필드를 표에 추가해도 아무도
> 막지 못합니다. 원칙은 강제되지 않으면 결국 잊힙니다.

## 이름에 담은 것 — `_plus_patch`

**본체에 얹는 부가 교정, 언제든 분리 가능**이라는 뜻입니다.

- `account_kr_plus_patch` → `account_kr_*` 계열에 얹음
- `mrp_plus_patch` → `mrp` 계열에 얹음

이름 자체가 **"이건 임시 거처이고, 본체 편입이 목표"** 라는 신호입니다.
(같은 본능의 사례가 이 레포에 하나 더 있습니다 — `escon_mainmenu` 에서
갈라져 나온 `escon_mainmenu_do_redirect`)

## 기존 모듈과의 차이 (간단 비교)

### 성격

| | 기존 커스텀 모듈 대다수 | plus_patch 2종 |
|---|---|---|
| 목적 | 없는 기능을 **추가** | 이미 있는 동작을 **교정** |
| 산출물 | 모델·메뉴·뷰·워크플로 | 없음 (설정값 1개 + 필드 자리수) |
| 사용자 접점 | 새 화면·메뉴 | 없음 — 기존 화면의 숫자만 달라짐 |
| 제거하면 | 기능이 사라짐 | 원래 표시로 복귀, 손실 없음 |
| 소유권 | 해당 도메인 담당 | 임시 — 본체 편입이 목표 |

### 개별 비교

| 모듈 | 하는 일 | plus_patch 와의 차이 |
|---|---|---|
| `account_kr_guard` (K-Guard) | 결제 가드·사업자번호 중복 경고·마감 체크리스트 — **새 모델과 검증 로직** | plus_patch 는 새 모델 **0개**. 판단하지 않고 표시만 교정 |
| `account_kr_reports` (K-Reports) | 매입매출장·일월계표·K-재무제표 — **새 리포트와 메뉴** | plus_patch 는 새 메뉴 **0개**. 기존 화면에만 작용 |
| `escon_uom_standard` | 단위 기준 정책 마스터 + 위반 점검 | **가장 가까운 친척, 접근은 반대 방향** (아래 참조) |
| `account_menu_extend` | 회계 메뉴 추가 | 메뉴 추가 vs 표시 교정 |

### `escon_uom_standard` 와의 관계 — 경쟁이 아니라 보완

둘은 **같은 통증**(kg 원단위 소수점 잘림)에서 출발했지만 방향이 반대입니다.

- `escon_uom_standard`: 자리수가 0인 현실을 **받아들이고**, "g 단위로 입력하라"는
  정책과 위반 점검으로 우회 — **사람이 규칙을 지켜 피해 가는** 방식
- `mrp_plus_patch`: 자리수 소스 자체를 **교정** — **원인을 없애는** 방식

`escon_uom_standard` 의 단위 기준 정책은 여전히 유효합니다. 전사 단위 정합은
자리수와 무관하게 필요한 관리이고, 이제 그 정책이 **자리수 제약에 떠밀려서가
아니라 순수하게 관리 목적으로** 존재하게 됩니다. kg 입력도 안전해졌을 뿐입니다.

## 다음에 이 패턴을 쓸지 판단하는 기준

| 상황 | 선택 |
|---|---|
| 본체 모듈의 소유자가 따로 있고 수정이 민감 | **plus_patch** |
| 변경이 표시·설정 계층에서 끝남 | **plus_patch** |
| 언인스톨만으로 완전 원복이 가능 | **plus_patch** |
| 새 모델·메뉴·워크플로가 필요 | 본체 수정 또는 정식 신규 모듈 |
| 본체의 비즈니스 로직을 바꿔야 함 | 본체 수정 (소유자와 협의) |

plus_patch 는 **영구 거처가 아닙니다.** 본체에 편입되는 순간 제거되는 것이
정상적인 수명 주기입니다.
