# 무발주 부품 SCM 후보 — 2026-09-23

**상태: 구현 후보 / 런타임 미검증 / 미설치 / 미배포.**
기준: 별도 복사본 `fix/e2e-20260923`, 코드 기준 `266d51d`. 배포 이미지와 소스의 동일성은 별도 인계 증거로 확정해야 한다.
이 후보의 AST/XML 검증은 Odoo 설치·업무 E2E 통과를 의미하지 않는다. 기존 528건 보조회귀 결과를 이 후보의 통과 근거로 사용하지 않는다.

## 해결하려는 실제 공백

기존 `supplier.asn.action_create_picking`은 PO행 없이 들어온 ASN을 거부한다. 사용자의 부품 정책은 원청 계획을 공유받은 협력사가 PO 없이 선납하고, 당사는 확정 양품×생산 당시 BOM과 승인 가감으로 정산하는 것이다. 따라서 포털 수량통보 → ASN → 표준 입고를 별도 원천으로 연결했다.

## 사용자 흐름

1. 구매 관리자: 구매 메뉴의 **무발주 공급 협약**에서 회사·공급사·부품·입고 유형·협약 문서 근거·기간을 등록한다. 기본 비활성이다. 수지가 아닌 부품임을 확인하고 활성화한다. 같은 회사·공급사·품목의 활성 협약은 DB 고유 인덱스로 1개만 허용한다.
2. 구매 담당자: **부품 수량 요구통보**에서 관리번호·협약·제품 기본 단위·요구량·필요일·원청 계획 근거를 작성한다. 자동 계산된 발주서가 아니다. 발행 버튼으로 수정 불가능한 원본을 고정한다.
3. 근거 모드: `담당자 확인 계획 근거`는 문서 참조와 산출근거를 담당자가 책임지고 입력한다. `현재 소요전망 원본 복사`는 발행 시 회사·업체·제품·필요일의 실제 전망 값을 서버에서 복사한다. 전망 cron이 삭제·재생성해도 원본 JSON은 남는다. 실제 원청 계획 파일 업로드·전자서명 검증까지 자동으로 한다는 뜻은 아니다.
4. 협력사: 기존 SCM 인증을 거쳐 ASN 화면의 **발주서 없는 부품 수량통보 및 납품 등록** 링크(`/supplier/no-po`)로 간다. 본인 회사의 발행 통보만 표시된다. 실제 예정 수량·도착일·공급사 LOT를 등록하면 기존 납품패스(QR)로 연결된다. POST는 CSRF와 제출 UUID를 검사한다. 같은 폼 재전송은 동일 ASN을 반환하고 내용이 달라진 재전송은 거부한다.
5. 창고: 기존 ASN **입고전표 생성** 버튼/QR을 사용한다. 통보 원천일 때 신규 표준 stock.picking/move를 생성한다. 실입고 수량·LOT를 가정해서 채우지 않는다. 담당자가 계수 후 표준 입고 확인·IQC·백오더 절차를 수행한다. 품질 합격·면제를 임의 생성하지 않는다.
6. 부분납입: 완료 수량은 누계로 남고 기존 백오더가 재사용된다. 같은 ASN 버튼을 재클릭해도 중복 입고를 만들지 않는다. 백오더 취소 뒤 ASN 재접수 시 완료분을 뺀 잔량만 만든다.
7. 입고 전 취소: ASN의 미입고 이동 자체를 취소하고 원 연결을 보존한다. 기존 PO ASN처럼 연결만 제거하면 근거 없는 입고가 남으므로 별도 처리한다. 통보 취소 후 새 통보는 이전 취소 통보와 개정 사유를 연결한다.
8. 일부 납입 후 잔량 축소: 통보의 **미입고 잔량 종료**를 실행한다. 완료 입고는 보존하고 미완료 이동만 취소하며 ASN/통보는 `잔량 종료`가 된다. 후속 통보에는 **새로 필요한 잔량만** 적는다. 예: 원래10, 입고4, 남은 수요를3으로 줄이면 기존10/입고4 이력 보존 + 새 잔량통보3이다. 이미 납입한4를 다시 포함하지 않는다.

## 정책과 방어 범위

- 협약은 회사·상위 상업 거래처·재고 부품에 한정한다. 기존 supplierinfo 공급 범위도 확인한다. `settle_by_ton` 또는 수지 `purchase_order` 정책 표시가 있으면 거부한다. 아직 원재료로 분류되지 않은 잘못된 마스터까지 자동 판별하지 못하므로 관리자 명시 확인을 요구한다. 수지 정산 코드/단가/발주 정책은 수정하지 않는다.
- 활성 협약의 기간에 해당하는 신규 구매행/PO 확인 및 자동 외주 PO 생성은 거부한다. 기존 확정 PO의 입고/ASN은 기존 경로를 유지한다. 미전환 품목·공급사·회사의 PO는 그대로 동작한다. 자동 외주 계획을 자동으로 수량통보로 전환하는 기능은 없다. 담당자가 요구통보를 발행해야 한다.
- 무발주 ASN에는 한 요구통보만 사용한다(LOT별 복수 행은 가능). PO 원천과 통보 원천의 혼합, 둘 다 지정, 회사·공급사·제품 불일치를 차단한다.
- 요구량 ≥ 취소되지 않은 ASN 예약량 합계. ASN량 ≥ 완료/예정 입고 배정량 및 실제 완료량. 제품 기본단위 정밀도를 검사한다. 입고 UoM은 동일 분류만 허용하고 실입고량은 기본단위로 환산한다.
- 통보행을 UPDATE하여 배정/수정/취소를 직렬화한다. context 기본값으로 원천을 넣는 ORM 생성도 같은 잠금을 먼저 얻는다. 협약 활성화와 PO 최종승인은 회사·상업거래처·품목 범위의 PostgreSQL advisory transaction lock을 공유하며, 미결 RFQ/PO가 있으면 협약 활성화를 막는다. PostgreSQL repeatable-read 충돌 시 거래 재시도가 필요하며, **두 커서 동시시험은 아직 수행하지 않았다**.
- 입고 시 무발주 부품의 회사별 재고평가가 `manual_periodic`인지 다시 검사한다. 평가설정을 강제로 바꾸지 않는다. 전사 분류 수정 자체나 정상 PO 입고를 막지 않는다.
- 매입청구서·정산 적립·분개는 이 addon이 생성하지 않는다. 표준 stock_account의 수동 정기 평가에서 실제 account.move 증가가 0인지 런타임에서 확인해야 한다.
- 사일로/수지 PO, 확정 양품 BOM 정산, 공급사 주장량 대사, 가감 승인 코드는 변경하지 않는다. ASN·입고량으로 정산액을 대체하지 않는다.
- 통보 없는 수동 입고는 기존 표준 기능 그대로다. 이 후보가 수동 입고에 통보를 사후 귀속시키지는 않는다. 사후 임의 연결/재배정 대신 담당자가 중복을 대사해야 한다.
- 반품은 기존 표준 반품 이동 및 승인 정산 조정 대상이다. 이 후보의 `실입고 누계`는 원래 공급처→내부 완료량(총 입고량)이며 반품을 차감한 순매입/정산량이 아니다. 반품으로 요구통보/ASN 잔량을 자동 복구하지 않는다.
- 구매 관리자만 협약을 만들고 활성화한다. 구매 담당자는 통보 발행·취소·잔량종료를 처리하고 창고 담당자는 읽기/기존 ASN 입고 업무를 한다. 일반 포털 ORM 접근권한은 추가하지 않는다. 컨트롤러는 인증된 공급사·회사로 검색한 특정 통보에만 권한을 높여 등록한다.

## 독립 검증 요청

`tests/test_no_po_supply.py`: 26개 Odoo TransactionCase 후보. 생성·불변성·전망 삭제 생존·회사/공급사/품목·정밀도·ASN잔량·중복 클릭·무분개·취소·과납·부분입고·기간·권한·포털 멱등/위장·기존 PO·활성 협약 중복 PO 차단·직접 최종승인/증량/업체변경 우회·미결RFQ 협약활성 차단·부분잔량 종료·원재료 분류 방어를 포함한다.

반드시 격리된 **배포 UAT 사본**에 설치해서 확인한다. 제품 fixture는 `manual_periodic`/기본단위이며 2026년 협약은 가정이다. 실제 회사 초기정보를 덮어쓰는 설치 데이터는 없다.

우선 순서:
1. addon 설치/뷰·ACL 로딩 및 테스트 전체 실행. 테스트 실패를 우회하지 말고 후보를 수정한다.
2. 기존 PO·수지 PO·양품 BOM정산 회귀를 설치 전/후 같은 fixture로 비교한다.
3. 실제 UAT IQC 모듈 조합에서 공급사 포털 → ASN → 검사대기 입고 → 합격 전 소비 차단 → 승인 검사 후 소비 → 양품 정산까지 실행한다.
4. 실제 HTTP 로그인·토큰·CSRF·타 공급사/회사 거부 및 QR 입고를 확인한다. 현재 회귀의 컨트롤러 호출은 HTTP/브라우저 증거가 아니다.
5. 두 PostgreSQL 커서에서 통보10을 ASN6씩 동시에 예약, 같은 ASN 입고버튼 동시호출, 부분입고 완료/잔량종료 경쟁, 포털 같은 UUID 동시POST를 수행한다. 한 건 성공·다른 건 재시도/거부, 총량≤10을 확인한다.
6. 협약 활성화와 기존 RFQ 최종승인의 공통 advisory lock이 두 커서에서도 한쪽만 성립시키는지 확인한다. 코드는 보완됐지만 실제 경쟁까지 안전하다고 주장하지 않는다.

## 설치/이식 주의

미설치 기본(`auto_install=False`), 협약 기본 비활성, cron 없음. 운영 서버/공유 UAT 변경·커밋·푸시·배포는 하지 않았다. 평가 설정/계정/사용자/품목/협약 활성화를 자동 생성하지 않는다. 기존 모듈의 비공개 `_ASN_WRITE` capability를 재사용하므로 supplier_portal_purchase 인터페이스 변경 시 같이 회귀 검증해야 한다. 회계/재고 이력 생성 후 module uninstall로 되돌리지 말고 시험 DB 복원 절차를 사용한다.
